# BI-Wizard 자문 채팅 요약 (2026-10-16 기준)

이 문서는 클라우드 세션 밖에서 진행한 "자문 채팅"(보고 평가·결정·지시문 작성)에만 있던 내용을 남긴 것이다.
결정 원문과 구현 기록은 저장소(`docs/decisions/03b-*`, `docs/gate-status.md`, `docs/retrospective/fu1-harness-operations.md`)가 정본이다.
이 문서는 그 기록의 **근거와 운영 방식**을 보완한다.

## 1. 작업 구조

- **목적:** revfactory/harness 에이전트 팀을 구성·운영하는 방법을 배우는 것. 제품은 셀프서비스 BI 포털(BI-Wizard)이다.
- **환경:** 클라우드 Claude Code, 개인 GitHub 저장소 `mindwindows/BI-Wizard`
  - 플러그인은 클라우드에서 쓸 수 없어서 `.claude/skills/harness/`를 복사해 쓴다.
  - 환경변수 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`이 필요하다.
- **역할 분담:**
  - 클라우드 세션은 구현·검증·보고를 맡는다.
  - 사용자는 보고를 자문 채팅에 전달하고, 결정하고, PR을 병합한다.
  - 자문 채팅은 보고를 평가하고, 결정 항목을 정리하고, 지시문을 작성한다.
- **에이전트 7개:** researcher, env-engineer, architect, backend-dev, frontend-dev, qa-engineer, reviewer. 모두 sonnet이다.

## 2. 운영 원칙 (사용자 지시)

**금지 명령**
- `.env` 삭제, `rm -rf`, `git clean -fdx`, `git reset --hard`, `docker compose down -v`
- 일괄 `prune`
- 볼륨·이미지는 이름을 정확히 지정해서만 삭제한다.

**비밀값**
- 저장소, 이미지, 프런트 번들, 로그, `ps`, 이미지 inspect, 컨테이너 Cmd·Args에는 0건이어야 한다.
- 컨테이너 Env는 `.env`와 같은 등급으로 허용한다(2026-10-13 결정).

**사전 승인 대상**
- 새 환경변수
- 새 의존성
- 운영 지침 기준과 다른 설정
- 권한 확대
- 에이전트 모델 변경
- 승인된 계약(05·06)의 동작 변경. 오류 우선순위, 응답 코드, 판정 순서를 포함한다(2026-10-14 추가).
- 마이그레이션의 DROP은 "DROP 확인: 사용자 승인"으로 기록한다.

**적용 후 보고로 충분한 것**
- 권한을 줄이는 변경
- 비밀·로그 노출을 줄이는 변경
- 이 둘은 "적용 후 보고 항목"으로 따로 보고한다.

**브랜치·PR**
- main에는 직접 커밋·push하지 않는다. 작업은 `harness/setup`에서만 한다.
- 병합은 "Create a merge commit"만 쓴다. Squash·Rebase는 금지하고, "Delete branch"는 누르지 않는다.
- PR이 열려 있는 동안 `harness/setup`에 push한 커밋은 그 PR에 들어간다. 다음 단위는 병합 뒤 fast-forward 하고 시작한다.
- GitHub 병합은 "Merge pull request" → **"Confirm merge"** 두 번 눌러야 끝난다. 한 번만 눌러서 병합이 안 된 일이 있었다.

**세션 시작**
- main에서 연다.
- `origin/harness/setup`이 `origin/main`에 포함되는지, diff가 비었는지 확인한다.
- 그다음 `harness/setup`으로 전환하고 fast-forward 한다.

**데이터와 QA**
- 개인 저장소에 회사 실데이터를 넣지 않는다. 샘플은 합성 데이터만 쓴다.
- QA는 `.env`를 만들거나 고치지 않는다. `_workspace/qa/`의 더미 env와 `--env-file`을 쓴다.

**D3 규칙**
- SQL 문자열 조립과 변수 보간은 금지한다.
- 예외는 고정 SQL 마이그레이션, bootstrap의 비밀번호 리터럴(`:'var'`), 허용 목록 기반 런타임 DDL(`bi_app` 실행)뿐이다.

## 3. 검증 규칙 (운영 중 정립)

- **전체 재검증:** 제품 영향 경로가 바뀌면 전체 재검증을 한다.
  - 제품 영향 경로: `backend/`, `frontend/`, `superset/`, nginx, compose, Dockerfile, 마이그레이션, bootstrap, 설정
  - 전체 재검증 항목: 실제 PG 전체 pytest, 차분 전수, 프런트 전체, Superset 스모크(STRIP true·false), 비밀값 검사, 마이그레이션 왕복
- **범위 재검증:** 문서나 수동 스크립트만 바뀌면 범위 재검증으로 충분하다. diff로 제품 영향 경로 0건을 증명하고 ruff와 CI 검증을 돌린다.
- **프런트 시험 파일·시험 설정만 바뀐 경우:** diff 증명, 두 커밋의 dist 해시 동일, 프런트 전체로 대신할 수 있다(FU-4 선례).
- **QA 뒤 수정:** QA 뒤에 제품 코드가 한 줄이라도 바뀌면 다시 검증한다.
- **커밋 전 자체 점검:** 리드도 포함해 `.py`는 `ruff check`·`ruff format --check`, 프런트는 lint·typecheck를 돌린다.
- **멈춤 규칙:** 실패가 1건이라도 있으면 PR을 만들지 않고 멈춘다. FU-4에서 한 번 어겼고, 그 건만 사후 승인했으며 규칙은 유지한다.
- **병합 조건:** PR의 마지막 커밋이 전체 검증 커밋과 같거나, 그 사이 변경이 문서뿐이어야 한다.

## 4. 보고를 평가할 때 매번 본 것

1. 에이전트가 보고한 모델이 정의 파일(sonnet)과 같은가
2. `git log -1`과 `origin/harness/setup`이 같은가, 작업 트리가 깨끗한가
3. 검증한 커밋과 PR의 마지막 커밋이 같은가. 다르면 그 사이 diff가 무엇인가
4. 일부만 재실행한 검증을 전체 검증처럼 보고하지 않았는가
5. 지시와 다르게 한 것(계약 이탈, 설정 변경, 멈춤 규칙 위반)이 숨어 있지 않은가
6. "추정"과 "실측"이 구분됐는가. 원인을 "상류 현상" 등으로 추정만 하고 넘어가지 않았는가
7. 비밀값 검사가 실제로 어디까지 봤는가. Cmd만 보고 Env는 안 본 사례가 있었다.
8. 실제로 재현하지 못하고 모의로만 확인한 것이 무엇인가

## 5. 지시문 표준 구조

1. 결정 확정(근거 "사용자 결정 YYYY-MM-DD", 03b 기록)

6. 통과 시 PR(병합 금지), 보고 항목(PR 번호, 마지막 커밋, 전체 검증 커밋, 수치)

## 7. 사건과 교훈

- **오래된 커밋에서 세션이 열림:** `08c4ac0`에서 두 번 일어났다. 그래서 세션을 main에서 시작하는 규칙을 만들었다.
- **에이전트 모델 캐시:** 정의 파일을 바꿔도 기존 세션에는 반영되지 않는다. 새 세션을 열어야 한다.
- **"고친 뒤 검사 안 돌림"이 반복됨:** 1d의 부분 재실행, 1e-f의 QA 뒤 수정, 리드의 ruff 미실행. 그래서 재검증 규칙과 커밋 전 자체 점검 규칙을 만들었다.
- **`docker inspect` 0건 보고:** 실제로는 Cmd만 확인한 것이었다. 그래서 검사 범위를 명시하는 규칙을 만들었다.
- **세션의 자의적 진행:** B5 계약 이탈과 멈춤 규칙 위반이 있었다. 둘 다 세션이 스스로 보고해서 알게 됐다. 그래서 계약 변경을 사전 확인 대상으로 추가했다.
- **단정 표현:** 세션 보고의 "원인", "횟수" 단정은 회고 작성 때 reviewer가 기록과 대조해 고쳤다. 근거가 없으면 "기록 없음"으로 쓴다.

## 8. 사용자 업무 사실 (자문 중 진술)

- **팀과 데이터셋:** 팀마다 자기 탭과 형식이 있다. 원자료는 수기로 입력하고 로직으로 계산한다.
  - 마스터 탭이 같은 지표 구조로 집계한다.
  - 다른 팀 열람은 허용한다(모두 읽기, 내 팀 우선 정렬).
  - 팀당 정의 담당자와 입력 담당자가 여럿이다. 5팀, 팀당 데이터셋 10개 이하.
- **엑셀 구조:** 엑셀은 월이 열이다. 시스템은 "월 = 행"으로 저장한다. 기존 탭 이관은 불필요하다(팀이 다시 만듦).
- **단위와 수식:** 단위는 주로 월이고 일부 연, 최소 일이다. 수식 유형 1~4를 모두 쓰고, SUMIF는 월 안에서 쓴다. VLOOKUP은 드물다.
- **기준값:**
  - 엑셀의 고정 $ 참조이고 연도별로 관리한다. 연중 변동은 없고 같은 연도에는 일괄 적용한다.
  - 계획 값은 미리 넣을 수 있지만 실적 값은 나중에 확정된다.
  - 팀마다 쓰는 상수 항목은 다를 수 있지만, 정의가 다른 데이터를 한 그래프에 섞지 않는다.
  - 글자 기준값은 "1월", "2026년" 같은 시기 참조에 썼다.
- **엑셀 파일:** 5MB 이하
- **운영 환경:**
  - 모든 서비스는 컨테이너로 돌린다(추가 컨테이너 허용). 메인 플랫폼의 하위 경로로 접속한다.
  - 메모리는 전체 8GB이고, 모니터는 1920×1080이다.
  - 먼저 localhost에서 확인하고, 배포 때 관리자가 프록시를 조정한다.
