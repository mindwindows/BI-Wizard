## 1라운드 (2026-10-11, 사용자 결정): 8번 인증 진행 방식, B 생성 권한, A 수식 범위

### 1-1. 진행 방식 (U1, U2, U4)
- **U1 일정 변경 승인.** 인증은 `current_user` 한 곳으로 모으고, 로컬에서는 **스텁 신원**으로 B 이후 라운드를 진행한다. 팀 소속은 포털 안에서 관리하므로(아래 1-3) 메인 플랫폼의 팀 정보에 의존하지 않는다. (승인된 계획 "B와 이후는 8번 답을 받은 뒤"에서 변경됨. 이 결정으로 8번의 **방식**(헤더/토큰/자체 로그인/SSO)은 계속 미결정이고, 운영 어댑터는 Gate ④ 중에 교체한다.)
- **U2 운영자 질문.** 20개를 `docs/operator-questions.md`로 저장하고 핵심 10개(1, 2, 5, 7, 8, 9, 13, 14, 15, 16번)를 표시한다. 사용자가 검토해 직접 답할 수 있는 것은 답하고, 남은 질문은 사용자가 운영자에게 전달한다.
- **U4 새 환경변수.** 각 방식이 정해지는 시점에 따로 승인받는다(적용 전 승인 규칙). 인증 스텁이 운영에서 켜지지 않게 하는 안전장치도 그 시점에 설계한다.

### 1-2. 업무 현실 (사용자 설명, 사실로 기록)
- 현재 엑셀 하나에 **팀별 탭**이 있고, 각 팀이 자기 양식을 자유롭게 정한다. **원본만 수기 입력**하고 나머지는 미리 넣은 수식으로 계산한다. 목적은 **제3자가 계산 근거를 확인**할 수 있게 하는 것이다.
- **master 탭**은 각 팀의 최종 계산값을 모아 요약한다. 모든 팀이 **같은 지표 구조**로 내고, 팀은 **어느 값이 최종값인지만 지정**한다.
- **다른 팀의 데이터와 계산 수식은 서로 봐도 된다.**
- **기준값**(전기·수도 요금, 본사 기준 등)은 별도 표에서 `$` 고정 참조로 쓴다. 지금은 연도별 탭이라 한 해 안에서 바뀌지 않는다. 새 시스템은 연도 구분 없이 계속 쌓일 수 있다. VLOOKUP식 키 매칭은 드물다.

### 1-3. B 생성 권한 (U5, U6 포함)
- **U6.** 팀(의뢰자)이 데이터셋을 **직접 만드는 것이 기본**이다.
- **U5.** **"정의 담당자"** (데이터셋 생성 + 열·수식 편집)와 **"입력자"** (데이터 입력만)를 분리한다.
- **B (팀 단위 소유).** 팀과 팀 소속은 **포털 안에서 관리자가 지정**한다. 팀 안에서 정의 담당자와 입력자를 구분한다. **관리자는 팀·소속 관리**를 맡는다. (브리프 5절 3번의 옵션 B3 "팀별 담당자"에 해당하되 팀 정보 출처가 포털이다. 기존 옵션 B1/B2/B2'는 채택하지 않았다.)
- **기준값 표와 공통 요약 양식의 편집 권한:** 관리자를 기본안으로 하되 옵션을 제시해 사용자 확인을 받는다 → **2라운드 질문 Q-R1**.
- **열람.** 인증된 포털 사용자는 **모든 팀의 데이터와 계산 수식을 볼 수 있다.** 팀 단위 열람 제한(RLS)은 필요 없다. 이 결정이 4라운드 I(RLS)·G(guest 역할)에 주는 영향은 아래 1-6.
- **새 요구사항(계산 근거 공개).** 데이터를 보는 사람이 **각 계산 열의 수식도 볼 수 있어야 한다.**

### 1-4. A 수식 범위
- **지원:** 같은 행 계산, 이전 행 참조(누적합·증감), **같은 데이터셋 안의 집계**. 같은 데이터셋 집계 중 Superset 차트로 대신할 수 있는 것은 수식에서 제외할 수 있다(세부는 07에서 제안).
- **기준값.** "**이름 + 값 + 적용 시작일**"로 관리하는 **기준값 표**를 두고, 수식에서는 **이름**으로 부르며 **각 행의 기준 날짜**에 해당하는 값을 쓴다. 기준 변경은 새 적용 시작일로 값을 추가하는 방식이며 **과거 결과는 보존**한다.
- **제외(첫 버전).** VLOOKUP식 키 매칭과 **일반 데이터셋 사이의 수식 참조**는 지원하지 않는다.
- **master 탭 기능은 수식이 아니라 "공통 요약 양식"** 으로 구현한다. 관리자가 공통 지표 양식을 정하고, 각 팀은 자기 최종값 열을 공통 지표에 연결하며, 포털이 이를 **하나의 요약 데이터로 모은다**. 합산·비교는 Superset 차트에서 한다.
- **기준 날짜 열.** 이전 행 참조와 기준값 적용을 위해 데이터셋마다 "기준 날짜 열" 지정이 필요하다. **필수로 할지 권장으로 할지**는 옵션으로 제시한다 → **2라운드 질문 Q-R2**.
- (영향) 위 결정으로 이전 비교안의 옵션 A(a)/(b)/(c)와 다른 범위가 확정됐다. "(a)+(c1) 조합"과 "행 간 참조"는 지원 쪽으로, 다른 표 참조(b/c2)는 제외로 정리된다.

### 1-5. U10, U11
- **U10.** 여러 데이터셋을 하나의 차트로 합치는 기능은 **필요 없다.** 서로 다른 데이터셋으로 만든 차트를 **한 대시보드에 나란히 배치**하는 것이 요구사항이며 Superset 대시보드 기본 기능으로 처리한다. **대시보드 전체 필터(날짜·팀)** 가 여러 데이터셋에 걸쳐 동작하도록, **기준 날짜·팀 같은 공통 열의 이름과 형식을 포털 차원에서 통일**하는 방안을 설계한다(07/06에서). Superset 대시보드 필터가 여러 데이터셋에 적용되는 조건은 researcher가 공식 문서·소스로 확인한다 → 2라운드 0단계 사실 확인.
- **U11.** 다른 데이터셋의 값을 선택하게 하는 **참조 열(입력 검증용)** 을 첫 버전의 데이터셋 정의 기능에 포함한다. (조회 열 = 다른 표 값을 가져오는 계산용은 제외, 1-4와 일관)
- **U3, U8, U12, U13** 은 계획대로 이후 라운드에서 묻는다.

### 1-6. 영향 정리: 열람 제한(RLS) 불필요 결정이 4라운드 I, G에 주는 영향
아래는 사실(`facts-superset.md` Q9~Q12)과 위 결정을 연결한 **정리**이며, 4라운드 결정을 대신하지 않는다.
- **I (RLS `clause` 생성 규칙, `GUEST_TOKEN_VALIDATOR_HOOK`).**
  - 열람 제한이 없으므로 guest token의 `rls`는 항상 빈 목록으로 보낼 수 있다(요청 본문 스키마에서 `rls`는 `required=True`인 리스트이고 길이 검증이 없어 빈 배열이 통과한다: Superset 6.1.0 `superset/security/api.py`의 `GuestTokenCreateSchema`. 실제 응답은 런타임 확인 전).
  - RLS `clause`가 서버 검증 없이 SQL 조각으로 WHERE에 들어가는 위험(Q10)은 **`rls`를 항상 빈 목록으로 고정**하면 노출 면이 사라진다. 클라이언트가 보낸 `rls`를 backend가 받지 않는 규칙이 설계 항목이 된다.
  - 4라운드에서 정할 것은 `clause` 생성 규칙이 아니라 "`rls`는 항상 빈 목록" 규칙과 (선택) 검증 훅으로 이를 강제할지 여부, 그리고 직접 서명 경로(Q9)의 Secret 보관 범위로 줄어든다.
- **G (guest 역할 권한 목록).**
  - 모든 guest가 같은 `GUEST_ROLE_NAME` 역할을 받는 Superset 구조(Q9)와 "모든 인증 사용자가 모든 데이터를 본다"가 일치하므로, 팀별 guest 역할 구분이 필요 없다. **단일 최소 권한 커스텀 역할**로 충분하다.
  - `Public` 역할은 계속 비워 둔다(`@protect` API가 `Public` 권한을 guest에게도 통과시킴, Q12). `Gamma`·`PUBLIC_ROLE_LIKE`는 운영에 쓰지 않는다는 기존 결정은 그대로다.
  - guest token의 `resources`(허용 대시보드 목록)는 사용자 단위로 제한할 필요가 없다. 어떤 대시보드를 보여 줄지는 포털의 대시보드 연결 기능이 정한다.
  - 권한 목록 자체(embedded 최소 권한 집합)는 소스만으로 확정되지 않아 **런타임 실험이 필요**하다(Q12). 이 결정과 무관하게 4라운드에 남는다.
- **E (D2)에 주는 영향.** 팀별 DB 접근 제한이 필요 없으므로 `bi_readonly` 하나가 모든 동적 객체를 읽을 수 있어도 된다. 팀별 스키마 분리 같은 설계는 접근 제어가 아니라 정리·소유 표현이 필요할 때만 의미가 있다(2라운드 비교안에서 다룸).
- **8번 의존에 주는 영향.** 열람이 "인증된 모두"이고 팀 소속이 포털에서 관리되므로, 8번에서 필요한 최소 정보는 **변하지 않는 사용자 식별자**(와 선택적으로 이름)뿐이다. 부서·팀·역할을 플랫폼이 넘기는지는 필수 질문이 아니다(운영자 질문 5의 ④, 14, 15번은 참고 수준).
- **새 요구(계산 근거 공개)의 영향.** 수식 원문은 포털 DB가 가지므로 "수식 보기"는 포털 API로 제공한다(Superset 필요 없음). 이 API의 권한은 열람 권한(인증된 모두)이다. 05 API 계약과 07에서 수식 표시 형식(원문 중심 vs 열 이름으로 풀어 쓴 형태)을 정한다.

## 2라운드 (2026-10-11, 사용자 결정): 평가 경로 C(6번), 동적 객체 분리 D2, 기준값·요약·기준 날짜 열, 질문 W1~W12, 기본값 B1~B10, 런타임 실험 승인

### 2-1. 업무 현실 (사용자 설명, 사실로 기록)
- 현재 팀 탭은 **"행 = 항목(원본 입력 항목과 계산 항목), 열 = 월"** 구조다. 계산은 **같은 월 열 안에서 위아래 행을 참조**한다. master 탭은 각 월 열에서 **정해진 최종값 행**을 가져간다. **같은 월에 여러 줄이 생기는 일은 없다.**
- 데이터 단위는 **월 단위가 가장 흔하고 일부는 연 단위**다. **가장 작은 단위는 일이며 시각 단위는 없다.**
- 규모는 **현재 5개 팀, 팀당 데이터셋은 10개 이내**(최대 약 50개)로 예상한다.
- **기준값에는 숫자와 글자가 모두 있다.**

### 2-2. 저장·입력·이관 결정
- **저장은 "한 기간 = 한 행, 항목 = 열"로 고정**한다. 엑셀의 같은 월 열 안 계산은 **같은 행 계산**, 전월 비교는 **이전 행 참조**, 최종값 행은 **최종값 열**로 대응한다.
- **데이터 입력 화면도 "한 기간 = 한 행"으로 고정**한다. 행·열 전환 보기는 첫 버전에서 만들지 않는다. 저장 방식이 같으므로 필요해지면 나중에 **보기 전환만 추가**할 수 있게 설계를 막지 않는다.
- **기존 엑셀 이관은 웹 서비스 밖의 별도 명령줄 전처리 도구**로 한다. "월 = 열" 엑셀을 "월 = 행" 표로 바꾸며 **원본 입력 행만 변환**하고 계산 행은 제외한다(계산 수식은 웹에서 다시 정의하도록 안내). 운영 가이드에 따라 **도구 사용법 Skill**을 둔다. **위치와 기능 순서는 04-modules.md에서 제안**한다. 웹의 엑셀 가져오기 범위는 처음 결정대로 "표 형태"만이다.
- **데이터셋마다 "날짜 단위(일/월/연)" 속성**을 두고 **기준 날짜는 기간의 첫날**(예: 2026-03-01)로 저장한다. 입력 화면은 단위에 맞게 표시·검증한다.

| W5 | (a) 규모는 위 2-1대로이며 **X-9 실험 조건**으로 쓴다. (b) **기준값은 첫 버전부터 숫자와 글자를 모두 지원한다. 기준값마다 형식을 지정하고 수식 엔진이 형식을 검사한다.** ⚠ **추천안("숫자만, 첫 버전")과 다른 사용자 결정**이다 |
| W6 | **최종값은 기간 행마다 있는 값**(저장 형태 기준)이다. "최종값 열을 공통 지표에 연결" 설계를 유지한다 |
| W7 (C, 6번) | **C0 정적 검사를 기본으로, 값 미리보기는 C1-a**(뷰와 같은 변환기로 원본 전체를 계산하고 일부 행을 표시, 읽기 전용 트랜잭션과 타임아웃). C1-b, C2, C4는 채택하지 않았다 |
| W8 | **기준값·공통 지표 양식은 관리자, 최종값 연결은 팀 정의 담당자** |
| W9 | **추가만 가능**(새 적용 시작일은 기존 시작일보다 늦고 이미 입력된 데이터의 가장 늦은 기준 날짜보다도 늦어야 함, 즉 보존 조건 포함). **아직 쓰이지 않은 값은 관리자가 정정 가능** |
| W10 | 참조 열은 **입력 때 확인 + 점검 화면**(앱 수준 검증). 원본 목록에서 값을 지울 때의 처리는 미결정 11번에서 따로 정한다 |
| W11 | **3라운드로 미룬다.** 의뢰자가 Superset 화면에서 직접 차트를 만든다면 데이터셋 이름의 가독성이 셀프서비스에 직접 영향을 주므로 **D(Explore 제공 방식, 미결정 7번)와 함께** 정한다 |
| W12 | **팀 열 자동 추가 + 날짜 형식 통일.** X-5 결과에 따라 **날짜 열 이름 통일**로 바뀔 수 있다. (U10을 부분만 충족함을 인지하고 결정) |

### 2-4. 열람 정렬
- 전체 열람을 유지하되 **포털 목록에서 소속 팀의 데이터셋이 상단에 오도록 기본 정렬**한다.
- **대시보드 팀 필터의 기본값을 소속 팀으로 둘 수 있는지**도 3라운드에서 함께 검토한다.

### 2-5. B 기본값
- **B1~B10 기본값을 승인한다.** B1 공통 요약은 조회 때마다 모으는 뷰, B2 기준값 표는 정적 표(읽기 전용 계정에 직접 권한 없음, 포털 화면에서는 열람), B3 지표는 삭제 대신 사용 중지(11번에서 최종), B4 최종값 연결은 적용 시작일을 둠, B5 미리보기 행은 기준 날짜 최근 순, B6 입력 후 일정 시간 뒤 실행과 버튼, B8 팀 열은 불변 코드, B10 등록과 물리 객체 정합성은 "물리 객체 먼저 + 시작 시 대조".
- **B7은 같은 기간에 여러 행이 없는 업무라 사실상 해당 없음**으로 기록한다(단 행 고유 번호 열은 이전 행 순서와 점검의 안정성을 위해 둘지는 06에서 정함).
- **B9(이전 행 비교는 표 전체 순서)는 기본값대로** 한다. 같은 월 열 안 계산이 같은 행 계산으로 대응되고 전월 비교가 이전 행 참조이므로 그룹별 비교는 필요하지 않다.
