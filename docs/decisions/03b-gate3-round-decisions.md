## 1라운드 (2026-10-11, 사용자 결정): 8번 인증 진행 방식, B 생성 권한, A 수식 범위

### 1-1. 진행 방식 (U1, U2, U4)
- **U1 일정 변경 승인.** 인증은 `current_user` 한 곳으로 모으고, 로컬에서는 **스텁 신원**으로 B 이후 라운드를 진행한다. 팀 소속은 포털 안에서 관리하므로(아래 1-3) 메인 플랫폼의 팀 정보에 의존하지 않는다. (승인된 계획 "B와 이후는 8번 답을 받은 뒤"에서 변경됨. 이 결정으로 8번의 **방식**(헤더/토큰/자체 로그인/SSO)은 계속 미결정이고, 운영 어댑터는 Gate ④ 중에 교체한다.)
- **U2 운영자 질문.** 20개를 `docs/operator-questions.md`로 저장하고 핵심 10개(1, 2, 5, 7, 8, 9, 13, 14, 15, 16번)를 표시한다. 사용자가 검토해 직접 답할 수 있는 것은 답하고, 남은 질문은 사용자가 운영자에게 전달한다.
- **U4 새 환경변수.** 각 방식이 정해지는 시점에 따로 승인받는다(적용 전 승인 규칙). 인증 스텁이 운영에서 켜지지 않게 하는 안전장치도 그 시점에 설계한다.

### 1-2. 업무 현실 (사용자 설명, 사실로 기록)
- 현재 엑셀 하나에 **팀별 탭**이 있고, 각 팀이 자기 양식을 자유롭게 정한다. **원본만 수기 입력**하고 나머지는 미리 넣은 수식으로 계산한다. 목적은 **제3자가 계산 근거를 확인**할 수 있게 하는 것이다.
- **master 탭**은 각 팀의 최종 계산값을 모아 요약한다. 모든 팀이 **같은 지표 구조**로 내고, 팀은 **어느 값이 최종값인지만 지정**한다.
- **다른 팀의 데이터와 계산 수식은 서로 봐도 된다.**
- **기준값**(전기·수도 요금, 본사 기준 등)은 별도 표에서 `$` 고정 참조로 쓴다. 지금은 연도별 탭이라 한 해 안에서 바뀌지 않는다. 새 시스템은 연도 구분 없이 계속 쌓일 수 있다. VLOOKUP식 키 매칭은 드물다.

### 1-3. B 생성 권한 (U5, U6 포함)
- **U6.** 팀(의뢰자)이 데이터셋을 **직접 만드는 것이 기본**이다.
- **U5.** **"정의 담당자"** (데이터셋 생성 + 열·수식 편집)와 **"입력자"** (데이터 입력만)를 분리한다.
- **B (팀 단위 소유).** 팀과 팀 소속은 **포털 안에서 관리자가 지정**한다. 팀 안에서 정의 담당자와 입력자를 구분한다. **관리자는 팀·소속 관리**를 맡는다. (브리프 5절 3번의 옵션 B3 "팀별 담당자"에 해당하되 팀 정보 출처가 포털이다. 기존 옵션 B1/B2/B2'는 채택하지 않았다.)
- **기준값 표와 공통 요약 양식의 편집 권한:** 관리자를 기본안으로 하되 옵션을 제시해 사용자 확인을 받는다 → **2라운드 질문 Q-R1**.
- **열람.** 인증된 포털 사용자는 **모든 팀의 데이터와 계산 수식을 볼 수 있다.** 팀 단위 열람 제한(RLS)은 필요 없다. 이 결정이 4라운드 I(RLS)·G(guest 역할)에 주는 영향은 아래 1-6.
- **새 요구사항(계산 근거 공개).** 데이터를 보는 사람이 **각 계산 열의 수식도 볼 수 있어야 한다.**

### 1-4. A 수식 범위
- **지원:** 같은 행 계산, 이전 행 참조(누적합·증감), **같은 데이터셋 안의 집계**. 같은 데이터셋 집계 중 Superset 차트로 대신할 수 있는 것은 수식에서 제외할 수 있다(세부는 07에서 제안).
- **기준값.** "**이름 + 값 + 적용 시작일**"로 관리하는 **기준값 표**를 두고, 수식에서는 **이름**으로 부르며 **각 행의 기준 날짜**에 해당하는 값을 쓴다. 기준 변경은 새 적용 시작일로 값을 추가하는 방식이며 **과거 결과는 보존**한다.
- **제외(첫 버전).** VLOOKUP식 키 매칭과 **일반 데이터셋 사이의 수식 참조**는 지원하지 않는다.
- **master 탭 기능은 수식이 아니라 "공통 요약 양식"** 으로 구현한다. 관리자가 공통 지표 양식을 정하고, 각 팀은 자기 최종값 열을 공통 지표에 연결하며, 포털이 이를 **하나의 요약 데이터로 모은다**. 합산·비교는 Superset 차트에서 한다.
- **기준 날짜 열.** 이전 행 참조와 기준값 적용을 위해 데이터셋마다 "기준 날짜 열" 지정이 필요하다. **필수로 할지 권장으로 할지**는 옵션으로 제시한다 → **2라운드 질문 Q-R2**.
- (영향) 위 결정으로 이전 비교안의 옵션 A(a)/(b)/(c)와 다른 범위가 확정됐다. "(a)+(c1) 조합"과 "행 간 참조"는 지원 쪽으로, 다른 표 참조(b/c2)는 제외로 정리된다.

### 1-5. U10, U11
- **U10.** 여러 데이터셋을 하나의 차트로 합치는 기능은 **필요 없다.** 서로 다른 데이터셋으로 만든 차트를 **한 대시보드에 나란히 배치**하는 것이 요구사항이며 Superset 대시보드 기본 기능으로 처리한다. **대시보드 전체 필터(날짜·팀)** 가 여러 데이터셋에 걸쳐 동작하도록, **기준 날짜·팀 같은 공통 열의 이름과 형식을 포털 차원에서 통일**하는 방안을 설계한다(07/06에서). Superset 대시보드 필터가 여러 데이터셋에 적용되는 조건은 researcher가 공식 문서·소스로 확인한다 → 2라운드 0단계 사실 확인.
- **U11.** 다른 데이터셋의 값을 선택하게 하는 **참조 열(입력 검증용)** 을 첫 버전의 데이터셋 정의 기능에 포함한다. (조회 열 = 다른 표 값을 가져오는 계산용은 제외, 1-4와 일관)
- **U3, U8, U12, U13** 은 계획대로 이후 라운드에서 묻는다.

### 1-6. 영향 정리: 열람 제한(RLS) 불필요 결정이 4라운드 I, G에 주는 영향
아래는 사실(`facts-superset.md` Q9~Q12)과 위 결정을 연결한 **정리**이며, 4라운드 결정을 대신하지 않는다.
- **I (RLS `clause` 생성 규칙, `GUEST_TOKEN_VALIDATOR_HOOK`).**
  - 열람 제한이 없으므로 guest token의 `rls`는 항상 빈 목록으로 보낼 수 있다(요청 본문 스키마에서 `rls`는 `required=True`인 리스트이고 길이 검증이 없어 빈 배열이 통과한다: Superset 6.1.0 `superset/security/api.py`의 `GuestTokenCreateSchema`. 실제 응답은 런타임 확인 전).
  - RLS `clause`가 서버 검증 없이 SQL 조각으로 WHERE에 들어가는 위험(Q10)은 **`rls`를 항상 빈 목록으로 고정**하면 노출 면이 사라진다. 클라이언트가 보낸 `rls`를 backend가 받지 않는 규칙이 설계 항목이 된다.
  - 4라운드에서 정할 것은 `clause` 생성 규칙이 아니라 "`rls`는 항상 빈 목록" 규칙과 (선택) 검증 훅으로 이를 강제할지 여부, 그리고 직접 서명 경로(Q9)의 Secret 보관 범위로 줄어든다.
- **G (guest 역할 권한 목록).**
  - 모든 guest가 같은 `GUEST_ROLE_NAME` 역할을 받는 Superset 구조(Q9)와 "모든 인증 사용자가 모든 데이터를 본다"가 일치하므로, 팀별 guest 역할 구분이 필요 없다. **단일 최소 권한 커스텀 역할**로 충분하다.
  - `Public` 역할은 계속 비워 둔다(`@protect` API가 `Public` 권한을 guest에게도 통과시킴, Q12). `Gamma`·`PUBLIC_ROLE_LIKE`는 운영에 쓰지 않는다는 기존 결정은 그대로다.
  - guest token의 `resources`(허용 대시보드 목록)는 사용자 단위로 제한할 필요가 없다. 어떤 대시보드를 보여 줄지는 포털의 대시보드 연결 기능이 정한다.
  - 권한 목록 자체(embedded 최소 권한 집합)는 소스만으로 확정되지 않아 **런타임 실험이 필요**하다(Q12). 이 결정과 무관하게 4라운드에 남는다.
- **E (D2)에 주는 영향.** 팀별 DB 접근 제한이 필요 없으므로 `bi_readonly` 하나가 모든 동적 객체를 읽을 수 있어도 된다. 팀별 스키마 분리 같은 설계는 접근 제어가 아니라 정리·소유 표현이 필요할 때만 의미가 있다(2라운드 비교안에서 다룸).
- **8번 의존에 주는 영향.** 열람이 "인증된 모두"이고 팀 소속이 포털에서 관리되므로, 8번에서 필요한 최소 정보는 **변하지 않는 사용자 식별자**(와 선택적으로 이름)뿐이다. 부서·팀·역할을 플랫폼이 넘기는지는 필수 질문이 아니다(운영자 질문 5의 ④, 14, 15번은 참고 수준).
- **새 요구(계산 근거 공개)의 영향.** 수식 원문은 포털 DB가 가지므로 "수식 보기"는 포털 API로 제공한다(Superset 필요 없음). 이 API의 권한은 열람 권한(인증된 모두)이다. 05 API 계약과 07에서 수식 표시 형식(원문 중심 vs 열 이름으로 풀어 쓴 형태)을 정한다.

## 2라운드 (2026-10-11, 사용자 결정): 평가 경로 C(6번), 동적 객체 분리 D2, 기준값·요약·기준 날짜 열, 질문 W1~W12, 기본값 B1~B10, 런타임 실험 승인

### 2-1. 업무 현실 (사용자 설명, 사실로 기록)
- 현재 팀 탭은 **"행 = 항목(원본 입력 항목과 계산 항목), 열 = 월"** 구조다. 계산은 **같은 월 열 안에서 위아래 행을 참조**한다. master 탭은 각 월 열에서 **정해진 최종값 행**을 가져간다. **같은 월에 여러 줄이 생기는 일은 없다.**
- 데이터 단위는 **월 단위가 가장 흔하고 일부는 연 단위**다. **가장 작은 단위는 일이며 시각 단위는 없다.**
- 규모는 **현재 5개 팀, 팀당 데이터셋은 10개 이내**(최대 약 50개)로 예상한다.
- **기준값에는 숫자와 글자가 모두 있다.**

### 2-2. 저장·입력·이관 결정
- **저장은 "한 기간 = 한 행, 항목 = 열"로 고정**한다. 엑셀의 같은 월 열 안 계산은 **같은 행 계산**, 전월 비교는 **이전 행 참조**, 최종값 행은 **최종값 열**로 대응한다.
- **데이터 입력 화면도 "한 기간 = 한 행"으로 고정**한다. 행·열 전환 보기는 첫 버전에서 만들지 않는다. 저장 방식이 같으므로 필요해지면 나중에 **보기 전환만 추가**할 수 있게 설계를 막지 않는다.
- **(4라운드에서 범위 제외로 취소, 4-6 참고)** 기존 엑셀 이관은 웹 서비스 밖의 별도 명령줄 전처리 도구로 한다. "월 = 열" 엑셀을 "월 = 행" 표로 바꾸며 **원본 입력 행만 변환**하고 계산 행은 제외한다(계산 수식은 웹에서 다시 정의하도록 안내). 운영 가이드에 따라 **도구 사용법 Skill**을 둔다. **위치와 기능 순서는 04-modules.md에서 제안**한다. 웹의 엑셀 가져오기 범위는 처음 결정대로 "표 형태"만이다.
- **데이터셋마다 "날짜 단위(일/월/연)" 속성**을 두고 **기준 날짜는 기간의 첫날**(예: 2026-03-01)로 저장한다. 입력 화면은 단위에 맞게 표시·검증한다.

## 3. 3라운드 결정 (2026-10-11, 사용자: "3라운드는 모두 추천안대로 확정")

옵션 비교와 근거는 `_workspace/gate3/round3-options.md`(Git 제외), 실험 결과는 `03c-gate3-experiment-results.md`. 질문 번호(Y1~Y13, BY1~BY11)는 그 문서의 번호다.

### 3-1. 차트 작성 (미결정 7번 D, Y3·Y4)
- **Y3:** (가) Superset 일반 화면을 **새 창 링크**로 열고 **별도 로그인**한다. 8번 인증이 정해지면 (나) 로그인 자동 연동으로 올리는 것을 목표로 기록한다. (다) 포털 안 iframe은 X-18 결과를 본 뒤 판단한다.
- **Y4:** (가) **각 팀 정의 담당자**가 차트를 만든다. 작성자 역할은 **Gamma 복사본을 조정한 커스텀 역할(ㄴ)** 과 **schema 단위 데이터 접근 보조 역할**로 한다(내장 `Gamma`를 사용자에게 직접 부여하지 않는다). 복사본이 같은 동작을 하는지는 X-20으로 확인한다.
- **Gate ② 문구 해석(명시):** "`Gamma`와 `PUBLIC_ROLE_LIKE`는 운영 설정에 쓰지 않는다"는 **임베딩 대시보드를 보는 guest 역할에만 적용된다.** 작성자 역할은 위 ㄴ(Gamma 복사본 + 보조 역할)이며 내장 `Gamma`를 직접 부여하지는 않는다. `Public` 역할은 계속 비워 두고 `PUBLIC_ROLE_LIKE`는 쓰지 않는다. (`03a` 5절, `gate-status.md`의 Gate ② 결과 결정 3, `bi-review`에 같은 문구로 반영)
- **불변식(기록):** **"Superset에 등록된 데이터는 모두 공개"** — Superset에 등록되는 모든 데이터는 인증된 모든 사용자에게 공개된다. 전원 공개가 아닌 데이터셋을 `bi_data`에 두려면 설계 변경(별도 승인)이 필요하다. 근거: 03c의 관찰(데이터셋 접근 권한이 없는 Gamma가 차트 생성 201, 6.1.0 소스에서도 생성 검증에 접근권 확인이 없음).

### 3-2. 계정 분리 (F, Y1·Y2)
- **Y1 (가):** 역할 2개 — **`bi_owner`**(마이그레이션·정적 표 소유)와 **`bi_app`**(런타임, `bi_data`에만 `CREATE`).
- **Y1 (나):** 다음 두 가지를 승인한다.
  - **ㄱ.** 빈 schema(`bi_data`) 생성을 마이그레이션에서 **db-bootstrap으로 이동**한다(03b 2-6 문구 변경, 이유: 비슈퍼유저 마이그레이션 계정이 schema를 만들려면 DB `CREATE` 권한이 필요한데 DB 이름이 변수라 D3 때문에 고정 문장으로 줄 수 없음). **이로써 D5(되돌리기 정책)의 의미가 "권한 상태 복원"으로 바뀌는 것(Y13 ㅊ)을 수용한다**: 첫 실제 revision의 `downgrade()`는 `bi_data` schema 자체를 지우지 않고, 왕복 테스트는 정적 표와 권한 상태가 복원되는지를 검증한다.
  - **ㄷ.** **B10 변경:** 데이터셋 등록(정적 표 `INSERT`) + 물리 표·뷰 + 권한 부여를 **한 트랜잭션**으로 처리하고, 시작 시 대조는 안전망(수동 변경·복원 사고용)으로 유지한다(03c X-1). 별도 DDL 로그인(F2-a) 구성은 이 결정과 맞지 않아 채택하지 않는다.
  - **ㄴ.** `bi_readonly` 읽기 권한 부여 위치(마이그레이션 유지 / db-bootstrap 이동)는 **X-14 결과 후 다시 묻는다.**
- **Y2 (가):** 전용 마이그레이션 계정 `bi_owner`(이름은 코드 상수). **새 환경변수 `POSTGRES_APP_PASSWORD`, `POSTGRES_OWNER_PASSWORD`를 승인한다.** `POSTGRES_USER`가 이미지 슈퍼유저 전용으로 좁아지는 것은 **운영 가이드 기준선과의 의도적 차이**로 `docs/deploy-coordination.md`에 기록한다(backend·migrate는 더 이상 `POSTGRES_USER`로 접속하지 않음).
- **D3 예외 2 문구 변경 승인:** "비밀번호 리터럴 두 곳"을 **새 계정 비밀번호까지 포함**하도록 바꾼다(`POSTGRES_READONLY_PASSWORD`, `SUPERSET_DB_PASSWORD`, `POSTGRES_APP_PASSWORD`, `POSTGRES_OWNER_PASSWORD`). **범위는 계속 `backend/bootstrap/`의 비밀번호 리터럴과 psql `:'var'` 인용으로 한정하며 식별자 보간 금지(`:"var"`, `format('%I')` 포함)는 유지한다.** 이에 따라 문구 "두 곳"은 "비밀번호 리터럴(`roles.sql` 등 `backend/bootstrap/`의 `PASSWORD :'var'`)"로 일반화한다.
- **적용 시점:** 위 계정·환경변수·`db-bootstrap` 변경의 실제 구현(compose, `.env.example`, `backend/bootstrap/`, `migrate` 서비스, 왕복 테스트, 권한 매트릭스 테스트)은 Gate ③ 설계(04~08) 후 **Gate ④ 진입 전**에 env-engineer가 한다. 지금은 설계 결정과 문서 기록만 한다.

### 3-3. Superset 등록·이름·필터 (10번, W11, Y5·Y6·Y7)
- **Y5 (나):** 데이터셋 **등록과 열 새로고침은 서버의 Superset 서비스 계정**이, **차트·대시보드는 사람**이 한다. HTTP 클라이언트는 **`httpx`**로 한다(허용형 라이선스, 현재 개발 의존성에만 있어 **운영 런타임 의존성으로 승격**). **새 환경변수 `SUPERSET_SERVICE_USER`, `SUPERSET_SERVICE_PASSWORD`와 `httpx` 의존성을 승인한다.** 임베드 켜기는 **관리자 수동**(Superset 화면). 서비스 계정은 최소 권한으로 만들고 관리자급 계정을 서버에 두지 않는다.
- **Y6 (다):** 읽기 쉬운 이름의 **가상 데이터셋**으로 등록한다(Y5 (나)와 짝). 이름 변경 때 뷰·차트 영향은 X-22로 확인한다.
- **Y7 (가):** 팀 필터는 **모두 같은 기본값**으로 시작한다. **소속 팀 기본값은 X-21 결과 후 다시 판단**한다.

### 3-4. 동시 편집 (미결정 9번, Y8·Y9)
- **Y8:** (a) 행 편집은 **칸 단위 값 비교 갱신**(같은 칸을 동시에 바꿀 때만 충돌, 다른 칸 동시 입력은 둘 다 반영). (b) 붙여넣기·가져오기는 **충돌이 있으면 전부 취소**하고 충돌 목록을 보여 준다. **정의 편집**(열·수식 변경)은 **데이터셋 단위 직렬화 + 정의 버전 확인**이다. "0행이면 충돌" 방식은 PostgreSQL 문서에 그렇게 쓰여 있지 않은 설계 판단이므로 X-24로 확인한다.
- **Y9:** (a) 같은 기간 행은 **기본 하나만**, 정의 담당자가 끌 수 있다(같은 날짜에 여러 행이 필요한 데이터셋은 엑셀 샘플을 본 뒤 정한다). (b) 입력한 행의 기간 수정은 **허용 + 확인창**(이미 있는 기간으로는 못 옮김, "전월 비교·기준값 적용이 바뀝니다"). (c) **기준 날짜 열의 타입 변경은 금지**한다(이름 변경은 가능, 형식을 바꾸려면 새 열로 옮김). **브리프 4.3 "타입 변경은 변환 미리보기 후 확인"의 기능 축소**로 기록한다(다른 열은 4.3 그대로, "의존 뷰 내리기 → 변경 → 재생성" 한 트랜잭션 + 변환 미리보기).

### 3-5. 삭제 정책 (미결정 11번, Y10~Y12)
- **Y10:** 데이터 행은 **보관(숨김)**. 목록·계산에서 빠지고 "삭제한 행" 보기에서 복구할 수 있다. **보관은 그 팀의 입력자·정의 담당자, 영구 삭제는 관리자만.**
- **Y11:** 열·수식·데이터셋은 **사용 중지/보관**(값은 보관, 되살릴 수 있음). **보관은 정의 담당자, 영구 삭제는 관리자만**(영향 미리보기와 확인 후, 데이터셋은 이름 입력 확인). **표·뷰 `DROP`은 보관 후 30일이 지난 뒤에만 허용**한다. **열의 `DROP COLUMN`은 지연 없이 관리자 확인 후 실행**한다. 이 기능은 서비스 화면의 삭제이며 마이그레이션의 `DROP` 사용자 확인 규칙과는 별개다.
- **Y12:** (a) 팀·사용자는 **삭제 대신 비활성화만**(관리자). (b) 참조 중인 값 삭제는 **막지 않고 "끊어진 참조"를 점검 화면에 표시**한다(W10). (c) **공통 지표·기준값 이름의 완전 삭제는 관리자만**(B3 "11번에서 최종"의 확정).
- 영향 차트·대시보드 수를 포털이 영구 삭제 전에 보여 주는 것은 Y5 (나) 구성에서 가능하다(서비스 계정이 Superset 연관 객체를 읽음).

### 3-6. 기본값과 승인 (BY1~BY11, Y13)

## 4. 3라운드 후속과 4라운드 결정 (2026-10-11, 사용자)

옵션 비교와 근거는 `_workspace/gate3/round4-options.md`(Git 제외), 실험 결과는 `03c`. 질문 번호(Z0~Z14, BZ1~BZ20)는 그 문서의 번호다.

### 4-1. 3라운드 후속 재질문
- **Z0 (Y1 ㄴ):** (i) `bi_readonly` 읽기 권한 부여(`USAGE ON SCHEMA`, `ALTER DEFAULT PRIVILEGES FOR ROLE bi_app … GRANT SELECT … TO bi_readonly`)는 **마이그레이션에 유지**한다(`03-migration-tool.md` 기존 문구 그대로). 이를 위해 **db-bootstrap에 `GRANT bi_app TO bi_owner WITH INHERIT TRUE, SET FALSE` 한 줄(고정 SQL)을 추가**하는 것을 승인한다(근거: 03c X-14, `INHERIT FALSE`는 거부됨). 매 기동 실행 시 같은 `GRANT`를 반복하는 동작은 X-29에서 확인한다.
- **Z13 (Y3 (다)):** (가) Superset 작성 화면은 **새 창 링크로 유지**한다(iframe 도입은 하지 않음. 필요해지면 그때 다시 결정).
- **Z14 (Y7):** (가) 팀 필터는 **모두 같은 기본값으로 시작**한다(소속 팀 기본값은 도입하지 않음).

### 4-2. G·I: guest 역할과 입장권(guest token)
- **Z1:** ㄱ guest 권한은 Superset 정의 **최소 21개에서 시작해 X-25로 줄인다.** ㄴ 임베드 대시보드의 **CSV·이미지 내보내기는 허용하지 않는다**(`can_csv` 등을 guest 역할에 넣지 않음).
- **Z2:** guest 역할은 **`superset-init` 코드로 매 기동 멱등 생성**한다. **`GUEST_ROLE_NAME=bi_guest` 설정 추가를 승인**한다(운영 가이드 기준선과 다른 설정). 목록의 권한이 Superset에 없으면 시작을 막고, 업그레이드 때 새 권한은 자동으로 추가하지 않는다(BZ3·BZ4).
- **Z3:** ㄱ guest token은 **서버가 Superset 발급 API를 호출**하며 **발급 전용 새 Superset 계정**을 쓴다(**환경변수 2개 승인**, 이름은 08에서 확정하되 후보 `SUPERSET_GUEST_ISSUER_USER`, `SUPERSET_GUEST_ISSUER_PASSWORD`). `GUEST_TOKEN_JWT_AUDIENCE`가 이 구성에 필요하면 그 변수도 승인한다(X-28에서 필요 여부 확인, 발급 API 경로에서는 필요 없을 것으로 추정). ㄴ **embedded uuid는 관리자가 수동 입력**한다(포털 관리 화면). 이로써 3라운드 Y5의 서비스 계정(데이터셋 등록)과 발급 전용 계정이 **분리**된다.
- **Z4:** `rls`는 **서버 코드가 항상 빈 목록**으로 만들고(클라이언트 입력 없음), **Superset 검증 훅(`GUEST_TOKEN_VALIDATOR_HOOK`, `superset_config.py` 설정 추가)이 한 번 더 확인**한다. 승인(기준선과 다른 설정).
- **Z5:** guest token 유효 시간은 **기본 5분**(설정 변경 없음).

### 4-3. J: 수식 속 글자 상수와 런타임 DDL
- **Z6:** 기본값 **"보류"**. **X-26 결과를 본 뒤 (가) SQLAlchemy 내장 부품 + 검증, (나) 글자를 별도 표에 저장 중에서만** 정한다. **(다) "첫 버전 금지"는 선택지에서 제외**한다: 2라운드 W5(b) "기준값에 글자 포함" 결정과 IF 비교 수식 사용과 충돌하기 때문이다.
- **Z7:** 런타임 DDL(표·뷰 만들기·바꾸기·지우기)은 **SQLAlchemy 내장 구성요소만 사용하고, 한 모듈 안에서만 하며, `text()`·`exec_driver_sql` 금지**다. 만들 수 있는 **객체 종류는 허용 목록(표·뷰·인덱스·제약)** 으로 제한하고, 열 타입 변경·열 이름 변경·`DROP … CASCADE`도 허용 목록에 포함한다. 03c X-15에서 드러난 `bi_data` 안 함수·시퀀스·타입 생성 가능성(권한 상승 경로)은 **이 허용 목록 규칙으로 막고** 시작 자가 점검·권한 매트릭스 시험으로 확인한다. **`bi-review` 새 규칙(7-4)을 승인**한다.

### 4-4. H: 업로드와 가져오기
- **Z8:** 업로드 상한 **10MB**. 값은 **새 환경변수 `APP_UPLOAD_MAX_MB` 하나**로 서버·프록시·화면이 공유한다(승인; 화면 공개 설정 규칙은 이 변수에 한해 예외로 08/05에서 구체화). **로컬 nginx `client_max_body_size` 변경을 승인**한다.
- **Z9:** 가져오기는 **전역 동시 1건 + 사용자당 1건**, **행 100,000 / 열 100 / 셀 2,000,000 / 붙여넣기 5,000행**. **BZ5의 사용자별 속도 제한(429, 발급 API)** 을 승인한다.
- **Z10:** **동기 처리 + 확정 때 재전송**(서버는 파일을 보관하지 않음).
- **Z11:** 원본 파일은 **이름·크기·해시 같은 정보만 보관**한다(파일 본문 미보관).
- **브리프 4.7 이탈 승인:** **pandas를 쓰지 않고 openpyxl read-only를 사용**한다(브리프 4.7 기술 구성에 반영). openpyxl 등 런타임 의존성은 **기능 단위 착수 때** 요청한다(BZ19).

## 5. 진행 방식 변경: Gate ③을 첫 기능 단위(FU-1) 범위로 좁힘 (2026-10-11, 사용자)

**지금까지의 결정(1~4절)은 모두 그대로 유효하다.** Gate ③ 설계 문서(04~08)는 FU-1에 필요한 범위만 간결하게 쓰고, 나머지는 해당 기능 단위에서 결정한다.

### 5-1. FU-1 범위
- **포함:** 데이터셋 만들기(열 정의: 타입, 필수·범위 검증, 기준 날짜 열, 날짜 단위) / 팀·정의 담당자·입력자 권한(인증 스텁) / 입력 그리드("한 기간 = 한 행", 엑셀 붙여넣기, 칸 단위 동시 편집) / 같은 행 수식과 수식 보기 / 수식 미리보기 / Superset 데이터셋 등록(서비스 계정)·포털 임베딩 대시보드 보기.
- **제외(후속 기능 단위에서 결정):** 기준값 표, 이전 행 참조, 같은 데이터셋 집계, 엑셀 가져오기, 참조 열, 공통 요약, 보관·삭제 정책, 변경 기록.

### 5-2. FU-1 결정
- **K2 (권한 단위):** ㄱ **팀 단위 권한.** ㄴ **여러 팀 소속 가능.** 한 팀에 정의 담당자와 입력자를 각각 여러 명 둘 수 있다(인원 제한 없음). **기능 축소 기록:** 브리프 4.3 "역할별 열 편집 권한"은 후속 기능으로 미룬다. 01 디자인의 "역할×데이터셋 격자" 권한 화면은 **"팀×사용자"로 바꾼다**(승인된 화면 구조 변경).
- **K3 (임시 인증):** ㄱ 시험용 사용자 여러 명. ㄴ 관리자 사전 등록. ㄷ 첫 관리자는 **서버 명령 한 줄**로 만든다(운영 서버 실행 가능 여부는 `deploy-coordination.md`에 운영자 확인 항목으로 추가했다, 35번). **스텁은 개발·시험 환경에서만 켜지고, 운영 환경 설정에서 스텁이 켜져 있으면 backend가 시작을 거부한다.** `bi-review`에 이를 차단 규칙(7-5)으로 추가했다. (스텁을 켜는 설정이 새 환경변수가 되면 이름과 함께 적용 전 승인을 요청한다. 후보 `AUTH_STUB_ENABLED`, 이 결정으로 승인된 것은 아님.)
- **K6 (수식 함수):** 핵심 세트 = 사칙연산·비교, `IF`·`AND`·`OR`·`NOT`·`IFERROR`, `ROUND`·`ROUNDUP`·`ROUNDDOWN`·`ABS`·`MIN`·`MAX`, `&`·`LEFT`·`RIGHT`·`LEN`·`TRIM`, `YEAR`·`MONTH`·`DATE` + **같은 행 `SUM`** + **열 구분 태그 기반 조건 합산**(엑셀의 같은 달 안 `SUMIF`에 해당. 같은 태그의 새 열은 자동 포함, 태그 변경 시 뷰 재생성·순환 검사). **수식 엔진은 "함수 사전" 구조**로 만들어 함수 추가가 사전 한 항목 + 시험 사례로 끝나게 한다.
- **K7 (엑셀과 다른 곳):** ㄱ **빈 칸은 0이 아니라 "미입력"으로 유지하고 계산 결과도 빈 값**(엑셀과 다르므로 수식 도움말에 명시). ㄴ 글자 비교는 대소문자 무시. ㄷ **계산 오류 칸은 빈 값으로 저장하고, 화면에서는 빈 칸과 구별되게 표시하며 점검 화면에 목록으로 보인다.**
