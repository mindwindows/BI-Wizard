## 1. 범위와 처리 흐름
- FU-1은 **같은 행 수식만**(`03b` 5-1). 열마다 수식 하나, 결과는 계산 열(`kind=formula`), 뷰 열 이름은 `c_<번호>`(K12 (나), 표시 이름 갱신 확인됨: 03c A-27).
- 문법 **[제안]**: 열 참조 `[열 이름]`(저장은 열 번호 참조 AST라 이름 변경에 안 깨짐, 03b 1-6; 열 이름에는 `[` `]` `"`·제어문자를 쓸 수 없게 해 수식 보기 `text`를 다시 읽어도 깨지지 않음, 06 §3-3), 글자 `"…"`(안의 `"`는 `""`), 숫자 `1234.5`, `TRUE`/`FALSE`, 함수 호출 `NAME(…)`(문법은 함수 이름을 모르고 사전이 해석). **날짜 상수와 `NULL` 상수는 없다**(날짜는 `DATE()`, 빈 값은 열 값에서만 생김). 우선순위는 엑셀과 같음(비교 < `&` < `+ -` < `* /` < 부호).

## 2. 함수 사전 (`03b` 5-2 K6: 함수 추가 = 사전 항목 1개 + 시험 사례)
### 2-1. 사전 항목 필드 (연산자도 같은 구조)
| 필드 | 내용 |
| --- | --- |
| `name`, `signature` | 수식 이름, 인수 목록(이름·허용 타입 number/text/boolean/date·필수/반복·상수 필수 여부), `returns`(타입 또는 규칙) |
| `null_policy` | `propagate`(기본: 어느 인수라도 비면 결과도 빔, 사전 공통 감싸기가 처리) / `skip`(FU-1 함수는 쓰지 않음, 후속 "건너뛰는 합계"용) / `custom`(IF·AND·IFERROR 등 직접 처리) |
| `error_when` | (조건 식, 오류 코드) 목록. 평가 순서: 인수 오류 > 인수 빈 값 > 자기 조건. 오류 식은 값 식과 같은 구조(IF는 고른 쪽만) |
| `to_sql` | 인수 표현식 → 값 식. SQLAlchemy 내장 구성요소만, 상수·NULL은 §4-1 렌더러 경유 |
| `excel_diff`, `help_ko` | 엑셀과 차이, 편집기·수식 도움말 문구(도움말은 사전에서 자동 생성) |
| `cases` | 시험 사례(필수): 입력(상수·열 값·빈 값) → 기대 값 또는 오류 코드 또는 C0 거부 |
- 추가 절차: ① 사전 항목 1개 + `cases` 작성 ② 시험 실행(항목 완결성 검사 + §6 차분 매트릭스가 자동 확대) ③ 끝. 파서·C0·변환기·편집기·도움말은 수정하지 않는다. 변환 결과 SQL이 바뀌면 해시가 달라져 시작 때 해당 뷰만 재생성된다(§8).
- **K6 원칙의 예외(FU-3 `REF`, 한 번뿐):** `REF`는 "사전 항목 1개 + 시험"으로 끝나지 않는다. 행의 기준 날짜 열과 기준값 항목 목록(**환경 `ReferenceEnv`**)을 C0와 변환기가 알아야 하고(§3-2), 뷰 게이트(06 §3-4)와 마이그레이션 `0009`도 필요하기 때문이다. 대신 엔진에 **확장점 하나**를 더한다: 사전 항목이 선택적으로 `precheck`(C0에서 환경을 읽어 오류를 내는 콜백)와 환경을 읽는 `to_sql`을 가진다. 이후 환경이 필요한 함수(이전 행 참조 등 FU-4)는 같은 확장점에 항목만 더한다는 것이 합격선이고, 환경이 필요 없는 기존 함수의 추가 절차는 그대로다.

- **E4 (FU-3):** 문구 제안 "이 행의 기준 날짜가 속한 연도의 기준값이 등록되어 있지 않아 계산하지 못했습니다. 기준값 화면에서 그 연도 값을 추가하세요." 다른 셀 오류와 같은 경로로 노출된다: 오류 코드 사전(`CELL_ERROR_MESSAGES_KO`)에 한 줄 더하면 D1 `cell_errors`·`de_<번호>`의 `e_<열>`(smallint **4**)·그리드 `errors`·점검 화면 S5(D7·D8)가 모두 따라온다. **점검 화면 노출 경로 = `de_` 보조 뷰**(06 §3-4): `REF`를 쓴 열의 `e_<열>`이 4인 행이 D8 목록에 나오고 그 열의 오류 칸 수가 D7·D6 `error_count`에 잡힌다. 한계: 오류 칸 코드는 숫자 하나라 **어느 항목·연도가 없는지는 담지 않는다**(수식 보기와 그 행의 기준 날짜로 확인한다, 항목·연도 표시는 후속). 호스트 수식(`REF`를 인수로 쓰는 수식)의 오류는 인수 오류 우선 규칙(§2-1 `error_when` 평가 순서)에 따라 E4가 전파되고 `IFERROR`는 E4도 대체한다.

## 3. 의미 규칙 (`03b` 5-2 K7)
| 규칙 | 내용 | 수식 도움말 문구 제안 |
| --- | --- | --- |
| 미입력 | 0이 아니라 NULL 유지, 결과도 빈 값(함수별 `null_policy`) | "비어 있는 칸은 0이 아닙니다. 계산에 쓴 칸 중 하나라도 비어 있으면 결과도 빈 값입니다. (엑셀은 빈 칸을 0으로 계산합니다.)" |
| 오류 칸 | 값은 빈 값(NULL) + 오류 코드는 §3-1. 0 나누기·날짜 범위·기준값 없음(E4) 등은 전부 이 규칙, DB 예외로 뷰 조회가 깨지면 안 됨. 피할 수 없는 대체값은 `IFERROR` | "0으로 나누는 것처럼 계산할 수 없는 칸은 빈 값이 되고 점검 화면에 표시됩니다. 다른 값을 쓰려면 IFERROR를 쓰세요." |
| 글자 비교 | `=`·`<>`만, 양쪽 `lower()`. `lower()`의 DB 로케일 의존은 확인하지 못함 | "글자 비교는 대문자·소문자를 구별하지 않습니다." |
| 형 변환 | 숫자·글자·날짜 사이 자동 변환 없음. 어긋나면 C0 오류(날짜-글자 직접 비교 포함) | 쉬운 말 오류 문구 |
| 정규화 | 글자 상수·입력 값은 NFC로 정규화 **[제안, entry·05·06 영향]**. NFD와 NFC는 DB에서 `=`이 거짓(X-26.4, 확인됨) | - |
| 숫자·시간 | 숫자는 모두 `NUMERIC`, 상수 38자리 이하. FU-1 함수에 현재 날짜가 없어 DB 시간대 영향 없음(`TODAY`는 후속, X-8) | - |
- 상수 오류는 DB에 보내지 않는다: PostgreSQL 16 문서가 "상수 `1/0`은 쓰이지 않는 `CASE` 갈래 안에서도 계획 시간에 실패할 수 있고 `CASE`는 철벽이 아니다"라고 명시(`sources/raw/pg16-func.sgml:18255-18265`, 확인됨). 그래서 `/`는 `NULLIF`로 막고, 상수만으로 이뤄진 부분식의 오류(`1/0`, `LEFT("a",-1)`, `DATE(0,1,1)`)는 C0가 거부한다. 방법 **[제안]**: 인수가 모두 상수인 부분식은 사전의 `error_when` 조건 식만(값 식은 실행하지 않음) §4-1 렌더러의 바인드 상수로 읽기 전용 트랜잭션 `SELECT`에 넣어 평가하고, 참이면 C0 거부한다. 사전에 이미 있는 조건 식을 한 번 더 쓸 뿐 파이썬 평가기를 따로 만들지 않으므로 E-C 이중 구현이 아니다. 상수 `SELECT` 한 번에 여러 조건을 묶어 왕복을 줄인다.

- **환경 전달 (K6 예외의 구체):** `ReferenceEnv(item_ids: 이름→항목 번호 매핑, base_date_column_id: int | None)`를 `compile_formula`·`check_formula`·`compile_all`에 `env`로 넘기고, 변환기의 `ConvertContext`에 `reference_ids`와 `base_date_column_id`를 더한다. 변환기는 기준 날짜 열 식을 새 인수 없이 `ctx.source(base_date_column_id)`(이미 있는 열 번호 → `c_<번호>` 식 함수)로 얻는다. **C0 단계는 `env`로 두 오류를 판정하고(`precheck`), 변환 단계는 정수 상수 `item_ids[이름]`와 기준 날짜 식으로 서브쿼리를 만든다.**
- **변환 결과**(값 식 / 오류 식, `Compiled`): 값 = 스칼라 서브쿼리(06 §3-4 `REF` 행의 한 가지 모양, `public.reference_values` 표 객체는 `app/db_metadata.py`의 정적 표 정의를 재사용하되 변환기는 schema `public`을 명시한 복사본으로 쓴다 **[제안]**), 오류 = `CASE WHEN (같은 서브쿼리) IS NULL THEN 4 END`(smallint). `Compiled.type = number`, `const = None`(상수 부분식 검사 대상이 아님). 항목 이름은 SQL에 들어가지 않고 항목 번호(정수)만 `CAST(… AS INTEGER)`로 들어간다(§4-1).
- **의존 기록:** `REF`는 `formula_deps`에 아무 간선도 만들지 않는다(기준 날짜 열은 변경이 막힌 `raw` 열이라 순환이 생길 수 없고, 해제는 위 C0 오류로 막힌다). 수식 AST에는 `{"t":"call","n":"REF","a":[{"t":"text","v":"이름"}]}`로 저장되고 항목 **번호는 저장하지 않는다**(번호는 컴파일 때마다 이름에서 풀리며 항목은 삭제·이름 변경이 없어 안정적이다). 수식 보기(D6)는 일반 글자 상수 호출로 `REF("이름")`을 그대로 쓴다.
- **미리보기(C1-a)와 뷰가 같은 변환기:** D3 미리보기와 `dv_`·`de_`는 같은 `Compiled` 식을 쓰고 항목 번호 상수가 미리보기에서는 바인드, 뷰에서는 리터럴 렌더로 나가는 차이뿐이다(§6의 원칙 그대로, §4-1 정수 상수 렌더러 경유). 항목 번호는 DB 정수라 주입 표면이 늘지 않는다.
- **컴파일 호출 지점(6곳, 모두 `env`를 만들어 넘겨야 한다):** ① D2 `formula/service.py` `check`, ② D3 `preview`, ③ D4·D5 `_compile_for_save`, ④ D6 `view_formula`(`build_sql=False`, C0만), ⑤ 정의 변경 훅 `formula/hook.py` `apply_definition`의 `compile_all`(모든 저장 수식을 다시 컴파일하므로 B4·B5·B6·D4·D5·D10 재시도가 모두 여기를 지난다), ⑥ 시작 대조 `formula/reconcile.py` `view_needs_rebuild`의 `compile_all`. 환경은 한 곳(`reference` service의 항목 목록 읽기 + `DefinitionView.base_date_column_id`)에서 만드는 도우미 하나를 ①~⑥이 공유한다(`Context` 안에 `env`를 두고 ⑤·⑥은 `defn`에서 만듦). **`env`가 없으면(`None`) `REF`를 만나는 즉시 구현 오류(`RuntimeError`, 사용자 문구 아님)를 올린다 [제안: fail-closed. 호출 지점을 빠뜨리면 조용히 `REF_UNKNOWN`이 나오지 않고 시험에서 크게 실패하게 한다].** 시험: 위 6곳을 각각 `REF`가 있는 수식으로 실행해 같은 결과를 확인하고, `formula` 패키지 안의 `compile_formula`·`check_formula`·`compile_all` 호출이 모두 `env=`를 넘기는지 AST 검사로 확인한다.
- **기준값 값 변경과 뷰:** 정정(05 R5)·추가(R4)는 뷰 정의를 바꾸지 않으므로 `def_hash`가 같고 재생성이 없다(06 §3-4). 새 항목은 이미 저장된 수식에 영향이 없다(항목이 없어서 `REF_UNKNOWN`이던 수식은 저장되지 못했으므로 저장된 `REF`는 늘 풀린다). 시작 대조는 정상 경로에서 `REF` 뷰를 건너뛴다.

## 4. 리터럴과 글자 상수 (`03b` 5-2 Z6 (가))
SQLAlchemy 내장 `CreateView`가 `literal_binds`로 상수를 SQL 텍스트로 렌더한다(설치본 소스 `sql/ddl.py`, X-26, 확인됨). 공식 문서는 이 방식을 "debugging purposes only", "not to be passed to a live production database", "only with local, trusted input"으로 한정한다(`facts-db` Q6, 확인됨). 파라미터 없는 쿼리는 pg8000이 simple query로 보내 **여러 문장이 실행될 수 있다**(X-26, 확인됨). 방어는 우리 규칙과 시험에 달려 있다.
### 4-1. 타입 있는 리터럴 렌더러 (접점 한 곳, 나중에 (나)안으로 옮길 때 이 한 곳만 교체)
| 값 | 뷰와 미리보기가 같은 형태로 렌더 | 거부·제한 |
| --- | --- | --- |
| 숫자 | 유한 `Decimal` → `CAST(… AS NUMERIC)`. 정수도 `Decimal`로 전달(`10**30`의 BIGINT 범위 오류 제거) | `NaN`·`Infinity`(따옴표 없이 렌더되어 열 이름으로 해석됨, X-26.1), 38자리 초과 |

| 참거짓 / 날짜 | `CAST(true AS BOOLEAN)` / `CAST('YYYY-MM-DD' AS DATE)`(날짜 상수는 후속 단위, FU-1은 `DATE()` 결과만) | 날짜-글자 직접 비교 금지(C0) |
| 빈 값(사전 내부) | `CAST(NULL AS <형>)` | 형 없는 NULL 금지(바인드 `42P18`, X-26.3) |
| 사전 내부 상수(10, 1 등) | 전부 이 렌더러 경유 | 사전 코드의 `literal()`·`bindparam` 직접 호출을 코드 검사로 0건 확인 |
| 연산자 | `%` 연산자는 문법·사전에 없음(pg8000 컴파일러가 `%%`를 내 뷰 생성이 오류, X-26.3). 필요하면 `mod()` 함수 | - |
| 정수 상수(FU-3, `REF`의 항목 번호 전용) | 유한한 파이썬 `int` → `CAST(… AS INTEGER)`(미리보기는 바인드, 뷰는 리터럴 렌더). `Decimal`·`NUMERIC` 상수로 쓰지 않는다: `item_id`(integer)와 numeric을 비교하면 열에 캐스트가 걸려 인덱스를 못 쓰기 때문 | `bool`·음수·`INTEGER` 범위 밖은 거부. 사전 코드의 직접 `literal()` 금지 규칙(위)과 같은 코드 검사 대상 |

## 6. 미리보기와 뷰 결과 일치 (합격 기준 "불일치 0건", `03b` 5-2)
같은 표현식 객체에서 미리보기는 바인드, 뷰는 리터럴 렌더로 나가므로 차이는 상수 렌더와 상수의 DB 형 추론에서만 생긴다. 평범한 `literal()`은 346건 중 98건이 달랐고 `CAST` 후에도 22건이 남았다(X-26.3, 확인됨). 원인과 설계:
| 남은 22건의 원인 (X-26.3) | 건수 | 설계 |
| --- | --- | --- |
| 바인드만 오류: `10**30`이 BIGINT 범위 초과 | 11 | 모든 숫자 상수 `Decimal` → `CAST NUMERIC`(§4-1) |
| 바인드만 오류: 날짜와 글자 직접 비교 | 3 | C0가 거부(§3 형 변환 규칙) |
| 뷰만 오류: `%` 연산자 | 5 | 문법·사전에 `%` 없음(`mod()`는 FU-1 함수 세트에 없고 후속) |
| 양쪽 오류: `10**30 % 7`, `0/0`, `None + 1` | 3 | 결과는 같지만 메시지 차이를 막으려 모두 "수식 오류"로 정규화: `%`는 문법 밖, `0/0`은 상수 오류라 C0 거부(열 값 0은 오류 칸), `None`은 상수로 존재하지 않음(빈 값은 열 값). 변환 뒤에도 DB 예외가 나오면 시험 실패 |
- **차분(differential) 시험 매트릭스** = 합격 기준(원 346건은 전수가 아니었으므로 확대, 사전 항목이 늘면 자동 확대):
| 축 | 내용 |
| --- | --- |
| 함수 × 인수 구성 | 사전 전체(연산자 포함) × 타입이 유효한 조합. 2인수까지 전수, 3개 이상은 쌍별 **[제안]** |
| 값 변형 | 숫자 {0, 1, -1, 0.1, 0.5, 1.5, 2.5, -2.5, 1E-7, 10**30, 38자리}, 글자 {빈 문자열, 한글, `O'Brien`, 대소문자 혼합, 앞뒤·안쪽 연속 공백, NFC/NFD 쌍, 200자}, 참거짓, 날짜 {윤일, 월말, 0001-01-01, 9999-12-31}, 빈 값 |
| 출처 | 수식 상수 / 원본 열 값 / 계산 열 참조(펼침) |
| 비교 항목 | 값 문자 표기, `pg_typeof`, 오류 코드, DB 예외 여부 — 미리보기 결과 vs 뷰 읽기 결과 |
| 합격 | 불일치 0건, DB 예외 0건, C0 거부 기대 사례는 양쪽 모두 거부 |
- **`REF` 전용 묶음(FU-3, 기존 매트릭스에 더해 사전 항목 `REF`가 자동 확대되는 것과 별도로 고정 사례를 둔다):** 비교 항목은 위 표와 같다(값 문자 표기, `pg_typeof`, 오류 코드, DB 예외, 미리보기 vs 뷰)이고 **세 번째 기준으로 "파이썬 독립 기대값"**을 더한다: 파이썬 `Decimal` 사전 `{(항목, 연도): 값}`과 행의 `date.year`로 행별 기대 값·오류(E4)를 계산하는 독립 구현(SQL·SQLAlchemy 불사용)과 미리보기·뷰 결과가 모두 같아야 한다.
  | 사례 | 내용 |
  | --- | --- |
  | 연도 일치 | 같은 항목에 여러 연도 값이 있을 때 행의 기준 날짜 연도의 값만 쓰임. 항목 둘 이상·같은 항목 두 번 호출 |
  | 연도 누락 E4 | 연도 값 없음 → 값 NULL + `e_`=4, **이월 없음**(전년·다음 연도 값이 있어도 NULL), 항목에 연도 값이 0개, `year` CHECK 밖 연도의 기준 날짜(0001-01-01 등)도 E4, 9999-12-31은 9999년 값이 있으면 값 |
  | 정정 전후 | R5 정정 직후 미리보기·뷰 값이 새 값, **뷰 정의 해시·`def_hash` 불변·`CREATE`·`ALTER`·`DROP` 0건**(보관 시험 방식의 문장 로그), 정정된 연도 외 행은 불변. 추가(R4) 직후 E4였던 행이 값으로 바뀜 |
  | 연도 경계·윤일 | 12-31과 다음 해 1-1, 2024-02-29, `date_unit` 일/월/연(월·연 단위는 기간 첫날 CHECK로 1일만 가능하므로 12-31 경계는 일 단위에서만) |
  | 숙주 수식 | `[열]*REF`, `REF/[열]`(열 값 0과 E4가 함께면 인수 오류 순서로 E4), `ROUND(REF,2)`, `SUM(REF,REF)`(둘 다 E4면 E4), `IF(조건, REF, 0)`(고르지 않은 쪽의 E4는 무시), `IFERROR(REF,0)`(E4 대체), 계산 열이 `REF`를 쓰는 다른 계산 열을 참조(펼침) |
  | C0·환경 | `REF()`·`REF("a",2024)`·`REF([글자열])`(`CONST_REQUIRED`)·`REF([날짜열])`·`REF(1)`(`ARG_TYPE`)·없는 이름·기준 날짜 열 없음·둘 다 해당(오류 2건)·NFD 이름(NFC로 일치), 이름에 `"` 등 금지 문자가 있는 항목은 만들 수 없음 |
  | 게이트(06 §3-4) | 정상 모양 통과 + 06 §3-4의 거부 목록 부정 시험 전부(양성 대조: 모양을 한 군데씩 깨뜨린 서브쿼리를 거부) |
  | 호출 지점 | 위 §3-2의 6곳이 같은 결과, `env` 누락은 구현 오류 |
- 의미 정확성은 차분이 못 잡으므로 별도 항목: NFC/NFD 정규화(§3), 문서화한 엑셀 차이 규칙(실제 Excel과의 대조는 하지 않음: 클라우드에 Excel 없음, 확인하지 못함), `ROUND` 경계값과 `lower()` 로케일.

| 항목 | 내용 |

| 직렬화 | 정의 편집·시작 시 재생성·재시도(05 D10)는 모두 트랜잭션 맨 앞에서 그 데이터셋의 `datasets` 행을 `FOR NO KEY UPDATE`로 잡는 **한 가지 잠금**을 쓴다(advisory 잠금 불사용). 편집은 `def_version`을 비교해 충돌이면 `DEFINITION_VERSION_MISMATCH`, 재생성·재시도는 버전을 올리지 않는다. 잠금 순서와 행 쓰기와의 관계는 06 §5 [제안] |

- 파서 규칙: ① 행 구분 `\r\n`·`\n`·단독 `\r`(따옴표 밖), 끝 구분자 하나 무시, 빈 중간 행 보존. ② `"`로 시작하면 따옴표 셀: `""`→`"`, 닫는 `"` 뒤가 탭·줄바꿈·입력 끝일 때만 닫힘, 안의 탭·줄바꿈은 내용, 안의 `\r\n`은 `\n`. ③ 따옴표 셀을 읽다 닫힘 조건이 안 맞으면 셀 시작으로 되돌려 따옴표 없는 셀로 다시 읽음(1회). ④ 되돌림 없이 끝까지 안 닫히면 **붙여넣기 거부**.
- ⑤ 공백 안 자름, NUL 거부, 행마다 셀 수가 달라도 허용. ⑥ 문자열 배열만 반환하고 숫자·날짜 해석은 열 타입 쪽에서 하며 모호하면 오류 표시. ⑦ 5,000행과 요청 상한(05 C4: A안 1MiB 이하 승인), 서버가 다시 검증.

## 10-1. 1d 구현에서 확정된 한도·형태 (**확정**, 2026-10-12 사용자 승인: 03b 21-1 결정 1)
07에 없던 구현 선택을 사용자가 승인해 확정했다. 걸렸을 때 나오는 쉬운 말 문구는 `skills/dataset-definition/SKILL.md`에 적었다.
- **수식 AST 깊이 40**: SQLAlchemy 컴파일 재귀 한도 실측에서 정했다. 부작용: 항이 41개 이상인 `a+b+c…` 사슬은 `TOO_DEEP`으로 거부되고 `SUM(…)`을 안내한다(왼쪽 결합이 깊이를 1씩 올림).
- **변환 결과 SQL 노드 5만(`TOO_COMPLEX`)**: 공유 부분 중복을 산술로 센 값. `IF`는 값식과 오류식에 하위 식이 둘 다 들어가 중첩마다 SQL이 두 배가 되어 중첩 `DATE` 3겹 안팎에서 걸린다.
- **단항 부호 `neg`** 연산자(AST 내부 연산자, 단항 `+`는 버림).
- **`DATE` E3 범위 확대**: 07 표(연 1~9999 밖, 일 ±100000 밖)에 더해 결과 날짜가 0001-01-01~9999-12-31을 벗어나면 E3(DB가 `date out of range`로 뷰 조회를 깨뜨리지 않게).
- **`ROUNDUP` 값식**: 07 표의 `sign(x)*ceil(abs(x)*10^n)/10^n`에서 나눗셈 정밀도 문제(PostgreSQL 몫 유효숫자 한도)를 피하도록 정확한 곱셈 형태로 변경(03b 20절 reviewer M3).
- 미리보기·뷰 차분 시험은 수식 5,552개·비교 칸 679,664개에서 불일치 0건(2026-10-12 QA 실측).

## 11. 후속 기능 단위에서 결정
- 이전 행 참조·누적합·증감과 뷰 층 나누기(윈도 함수), 순환 간선 종류. 일부 칸이 비는 것이 정상인 항목이 생기면 "건너뛰는 합계" 함수를 함수 사전에 추가(`03b` 6-1).
