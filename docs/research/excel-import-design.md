## 0. 한눈에 보기
| 항목 | 내용 |
| --- | --- |
| 범위 | 업로드한 `.xlsx`의 한 시트에서 값을 읽어 **기존 데이터셋**의 행으로 적재한다. 두 모양: (가) 이미 "한 기간 = 한 행" 표, (나) 팀 탭의 "행 = 항목, 열 = 월"을 **전치**해 "한 기간 = 한 행"으로 [제안]. 새 데이터셋 만들기는 2단계로 분리 [제안] |
| 결론 1 | 5MB 파일은 read-only로 열면 메모리가 작다: 최대 RSS 28~115MB(증가 2~90MB), 일반 모드는 272~754MB라 쓰지 않는다. backend `mem_limit` 1GiB 안에서 여유가 크고 **전량을 메모리에 모으지 말고 배치로 처리**하면 2,000,000칸도 40MB [실측] |
| 결론 2 | 병목은 메모리가 아니라 **시간**이다: 5MB 파싱 5~14초(최악 공유 문자열 13초, 2,000,000칸 14초), 칸 검증 포함 end-to-end 5~9초, 셀 상한 근처는 파싱·검증 19초 + 적재 18초 = 37초로 승인된 "확정 30초 목표"(03b Z10)를 넘는다 [실측] |
| 결론 3 | 현재 붙여넣기(C4)의 **행마다 INSERT는 가져오기에 쓸 수 없다**: 5,000행 8.2초, 20,000행 32.9초(100,000행은 약 165초로 외삽). 배치 INSERT(RETURNING 포함)는 100,000행 x 12열 11.3초 [실측] |
| 결론 4 | 변조 파일은 **사전 검사 없이는 위험**하다(200MB 폭탄이 openpyxl만으로 63.7초·589MB). 중앙 디렉터리 기반 사전 검사 프로토타입은 변조 29종을 모두 0~94ms에 거부했고 정상 6종·`docs/samples` 4종에서 거짓 양성 0 [실측] |
| 의존성 | `openpyxl==3.1.5`(+`et-xmlfile==2.0.0`), `defusedxml==0.7.1`, `python-multipart==0.0.32` 필요. `rapidfuzz==3.14.6`은 **1단계에서 불필요**(표준 `difflib`이 합성 사례에서 동등, 설치 12MB) [실측·제안]. 전부 허용형 라이선스, `pip-audit` 알려진 취약점 없음 [실측] |
| 사용자에게 필요한 것 | 열린 질문(9절, Q1·Q2는 2026-10-15 답을 받아 닫힘). 특히 같은 기간 재가져오기 정책, 감사 기록 범위, 행 삭제 부재(교체 불가)에 대한 판단 |
| 승인 필요 | 새 의존성 4개(전이 `et-xmlfile` 포함), 마이그레이션 `0010`(이력 표 + 감사 action 1개 + GRANT, downgrade `DROP` 사용자 확인), 05 신규 엔드포인트·오류 코드, nginx 위치별 상한, `APP_UPLOAD_MAX_MB` 구현(Z8로 승인됨) — 8절 |
| 소요(추정) | 4단계 합계 약 20~27시간(커밋 기준), 7절 |

### 2-1. 화면 단계 (01 디자인: 앞 두 단계 B 콘솔형, 이후 C의 미리보기 그리드 + Inspector 재사용 [결정, 01-design-direction])

| 4 미리보기 | "변환 결과 상위 20행"(기간 오름차순) + 요약(새 행·건너뜀·오류·경고) + 오류 목록 | I1 미리보기(같은 I1에 옵션 포함, 전송 2) | 오류는 셀 주소 단위, 200건에서 자르고 `details.truncated`·`details.total` 표시 [결정, 05 §1 잘림 표시] |

### 2-2. 방향별 변환
| 구분 | (가) 월 = 행 표 | (나) 월 = 열 → 전치 |
| --- | --- | --- |
| 머리글 | 열 이름 = 데이터셋 열 이름 후보(매핑) | 머리글 행의 **기간 칸**(날짜 해석 2-3), 왼쪽 글자 열 = 항목 이름 |
| 기간 | 매핑된 날짜 열(기준 날짜 열) | 기간 칸마다 **한 행**을 만든다(기간 오름차순). 열 위치가 아니라 해석된 날짜로 정렬 |
| 항목 | 열 | 항목 행마다 데이터셋 열 하나(최대 100개 → 항목 행 > 100이면 범위를 좁히라는 오류 `ITEM_OVER_LIMIT` [제안]) |
| 제외 | 열 단위 제외 | 합계·소계·빈 행(2-4), 사용자가 체크 해제한 행 |
| 결과 | 표의 행 그대로 | 항목 수 x 기간 수의 값을 기간 x 항목으로 뒤집음 |
- 전치 결과의 크기는 (기간 수 ≤ 100열) x (항목 수 ≤ 100)이라 최대 10,000칸이다. 파일이 5MB인 것은 항목 행이 수만 개인 경우(계산·소계 행 포함)뿐이며, 이때도 매핑하는 항목은 100개 이하여야 한다 [제안]. 시험: 5MB 파일(항목 16,170행 x 36개월)을 `item_cap=100`으로 처리하면 30MB·4.9초, 100개 상한 없이 전부 보관하면 114MB·7.0초 [실측].

### 2-3. 날짜(기간) 해석 [실측: 시제품 `headers.py`, 사례 46건 통과]
| 머리글 값 | 해석(월 단위) | 비고 |
| --- | --- | --- |
| 진짜 날짜 셀(`2026-03-17`) | 해당 월 첫날 `2026-03-01` | 월 중간이면 첫날로 보정 + 경고(Q14). 연 단위는 1월 1일 |
| 엑셀 일련번호 숫자(46023) | 날짜로 변환(범위 20000~73000) | 1~12 숫자는 월 번호, 1900~2200은 연 단위일 때만 연도 |
| `1월`, `12월` | 연도 힌트 필요 → 없으면 `NEEDS_YEAR` | 월이 줄어들면 다음 해(옵션, `11월 12월 1월` → 연도 넘김) |
| `2026년 1월`, `26년 3월`, `2026-01`, `2026.01`, `2026/1`, `01/2026` | 그대로 해석 | 전각 숫자는 NFKC로 정규화 |
| `Jan-26`, `Jan 2026`, `January 2026`, `Sept-2026` | 영어 월 이름 3글자 | 두 자리 연도는 2000년대로 보고 미리보기에 해석 결과 표시 |
| `1월(잠정)` | 끝의 괄호 주석 제거 | 같은 월이 두 열이면 `DUPLICATE_PERIOD` |
| `26.1`, `1/26` | 연월/월일 구별 불가 → `AMBIGUOUS` | 사용자가 형식 지정 |
| `2026 1Q`, `합계` | `BAD_FORMAT` | 분기는 지원하지 않음(날짜 단위는 일/월/연) |
- **연도 정보 위치**: 우선순위 사용자 지정 > 머리글 자체 > 시트 이름(`2026`) > 상단 5행 제목 셀(`2025년 월별 실적`) > 없음이면 사용자 입력 필수. 후보가 둘 이상(`2024~2026`)이면 자동 제안하지 않음 [실측: `suggest_year` 사례 통과]. 확인 화면에 항상 해석된 날짜를 보인다 [제안].
- `date_unit`: 월 단위 데이터셋은 기간 첫날로만 저장(기존 입력 규칙 `NOT_PERIOD_START`와 일관), 일 단위는 일까지 있는 값만 받음(`UNIT_MISMATCH`) [제안].

### 2-5. 기간 중복 [제안, 질문 Q6·Q7]
| 선택 | 동작 | 일관성 |
| --- | --- | --- |
| **오류(기본·권장)** | 이미 있는 기간이 있으면 **충돌 목록 모아 전부 취소**(`PERIOD_CONFLICT`와 같은 `conflicts[].kind="period"` 형식) | C4 붙여넣기의 "충돌 시 전부 취소"(03b Y8)와 같음. 동작 변경 없음 |
| 건너뛰기 | 이미 있는 기간은 쓰지 않고 건수만 보고 | 새 정책 (K8 "추가"에 해당) |
| 덮어쓰기 | 기존 행의 칸을 파일 값으로 갱신. 서버가 같은 트랜잭션에서 읽고 갱신하므로 `expected` 가드가 없다(가져오기 중 입력 차단으로 대신) | 파일의 빈 칸이 기존 값을 지우는지(Q7)가 필요. **C4가 막는 "기존 행의 기간 변경"과는 다른 경로이고 감사·되돌릴 방법(행 삭제·복구 없음)이 약해 사용자 결정 후 구현** |
| 파일 안 중복 | 같은 기간이 열(또는 행)로 두 번 있으면 `DUPLICATE_PERIOD`(두 셀 주소 모두 표시) | 어떤 선택에서도 오류 |
- "교체"(기존 행 전부 삭제 후 적재, K8)는 **행 삭제가 없어 불가능**하다. 행 삭제 단위(FU-2c) 뒤에 별도로 결정한다 [결정, 05 §2-3] [제안].

### 2-6. 셀 값 변환·검증 (기존 `backend/app/entry/values.py`의 `parse_cell`을 **재사용**) [제안]
| 열 타입 | 엑셀 값 → 처리 | 오류 코드(기존 필드 코드 재사용) |
| --- | --- | --- |
| number | 숫자 셀은 **15자리 유효숫자**로 반올림해 십진 문자열(`format(Decimal(f"{v:.15g}"), "f")`)로 만든 뒤 `parse_cell`에 넘긴다. 부동소수 잡음(`0.30000000000000004`)이 `decimals` 규칙을 위반하는 것을 막는다. 글자 숫자(`"12"`)는 `parse_cell` 규칙 그대로(쉼표·지수 거부). 불리언·날짜는 오류 | `BAD_FORMAT`, `OUT_OF_RANGE` |
| date | 날짜 셀 → `YYYY-MM-DD`(시각이 있으면 버리고 경고). 글자는 `YYYY-MM-DD`만. 시간만 있는 값은 오류 | `BAD_FORMAT`, `NOT_PERIOD_START` |
| boolean | 불리언 셀, 또는 기존 허용 글자(`true`·`예`·`참` 등) | `BAD_FORMAT` |
| text | NFC·앞뒤 공백 제거. **개행·탭이 든 셀은 기존 규칙상 오류**(Q16) | `BAD_FORMAT`, `TOO_LONG` |
| choice | `rules.options` 정확 일치 | `NOT_IN_OPTIONS` |
| 필수 열 | 비면 `REQUIRED`(기준 날짜 열 포함) | `REQUIRED` |
| 오류값 셀(`#DIV/0!` 등) | `values_only`로는 글자와 구별되지 않아 **고정 7개 리터럴 일치**를 오류로 취급 [실측: 타입 `e`, 값은 글자] | 새 코드 `CELL_ERROR` [제안] |
| `-`, `–`, `—` | 빈 칸(미입력)으로 보고 건수 경고(Q15) | - |
| 계산 열·기준값(`REF`) 열 | **대상 아님**(매핑 목록에서 제외). 기준값 표 자체는 가져오기 대상 아님(Q20) | `READ_ONLY` |
- 처리량: 제품 `parse_cell` 칸당 3.9µs → 600,000칸 2.3초, 2,000,000칸 약 8초 [실측]. 오류 위치는 `A1` 형식 셀 주소 [제안].
- OOXML 제어문자 이스케이프(`_x0001_`)는 openpyxl이 해제하지 않아 글자 그대로 읽힌다 [실측]. 위험은 낮지만 그대로 저장된다.

### 2-8. 한도와 오류 보고 [제안]
| 한도 | 값 | 검사 방식 |
| --- | --- | --- |
| 파일 크기 | `APP_UPLOAD_MAX_MB` | nginx → `Content-Length` → 읽은 바이트 수(5-3) |
| 행 | 100,000 | `iter_rows(max_row=100,001)`로 읽다가 초과 행에서 중단(경계 시험은 기존 실측 `import-r4-results.md` 3절 [결정 인용]) |
| 열 | 100 | `max_col=101`로 읽고 **값이 있는 마지막 열 번호**가 100을 넘으면 거부 |
| 셀 | 2,000,000 | **값이 있는 칸 수**로 센다. `iter_rows(max_col=101)`는 각 행을 101칸으로 채워 돌려주므로 길이로 세면 63만 칸 파일이 200만 칸으로 집계되어 잘못 중단됐다 [실측: 첫 측정에서 `m_col_12`가 19,802행에서 "셀 상한 초과"로 멈춤] |
| 시트 수 / 항목 행(전치) | 30 / 100 | 사전 검사 / 매핑 단계 |
| `<dimension>`·`ws.max_row` | **신뢰하지 않음** | 선언이 거짓이면 시간이 늘거나(`A1:XFD1048576`) 데이터가 조용히 잘린다는 기존 실측 [결정 인용, `import-r4-results.md` 5-2]. 항상 `iter_rows(max_row, max_col)` 상한으로 읽는다 |
| 시간 | 확정 45초 협조적 중단 | 행마다 시간 확인. 열기 단계는 협조적으로 중단할 수 없어 사전 검사의 크기 규칙이 대신한다 [제안 + 실측 5-2] |
- 오류 보고: `422 VALIDATION_ERROR`의 `details.fields[]`에 `{cell: "D12", column_id, code, message}`(엑셀 **셀 주소** 단위), 200건에서 자르고 `details.truncated: true`·`details.total`(전체 건수)을 함께 준다 [제안; 잘림 표시 방식은 05 §1 선례]. `cell` 키는 05에 없는 필드이므로 계약 추가다(8절 8번). 같은 오류 코드는 목록 위에서 코드별 건수로 요약해 보인다 [제안].
- 경고(오류 아님)는 건수 요약만 준다: 합계 행 제외 N, `-` 빈 칸 처리 N, 월 중간 날짜 보정 N, 수식 캐시 없음 N, 시각 버림 N [제안].

## 3. 데이터셋 정의와의 관계
| 경우 | 흐름 | 권한 | 단계 |
| --- | --- | --- | --- |
| 기존 데이터셋에 넣기 | 위 2-1 | 그 팀 `entry`·`definer` (C4와 같음, 관리자라도 소속이 아니면 403). 보관 중 409 `DATASET_ARCHIVED`, 비활성 사용자 403 [결정, data-entry Skill] | 1단계 |
| 새 데이터셋 만들기 | 분석 결과로 열 이름·형을 제안 → 정의 담당자가 수정 → B2 생성 → B5 열 추가 N번 → B4 기준 날짜 열 지정 → 가져오기. 가져오기 실패 시 **빈 데이터셋이 남고**(이름 점유 계속, 보관으로 정리) | 팀 `definer`(B2·B5·B4 권한) | 2단계 |
- 열 이름: 머리글/항목 이름을 그대로 쓰되 길이 100자, `[`·`]`·`"`·제어문자 금지, 예약어(`team`·`팀`·`row_id`·`행 번호`)·중복은 오류로 알리고 사용자가 고친다 [결정, 05 §1 이름 규칙] [제안].
- 형 추론: 열 값 샘플의 90% 이상이 한 형이면 그 형(숫자 → number, 날짜 셀 → date, 불리언 → boolean), 아니면 text. choice는 추론하지 않는다(정의 담당자가 수동). `required`는 모두 false. Grist `ColumnDetector`(90% 기준, `references/grist-core/`)를 구조만 참고해 재작성 [제안, 라이선스 Apache 2.0 복사 안 함].
- 기준 날짜 열: (나) 전치에서는 "기준월" 날짜 열을 자동으로 만들고 `date_unit` = 월로 지정(행이 0개일 때만 가능, B4) [제안]. (가)에서는 모든 값이 기간 첫날인 날짜 열을 후보로 제안.
- **B5는 열마다 `def_version`을 올리고 `ALTER TABLE`·뷰 재생성을 한다**: 열 100개를 순차 호출하는 시간은 측정하지 못했다 [확인 못 함]. 느리면 "열 여러 개를 한 번에 만드는" 정의 API가 필요하고 이는 **05 계약 변경**이다(8절).

## 4. 트랜잭션·잠금·감사·이력·권한 [제안]
| 항목 | 설계 |
| --- | --- |
| 잠금 | 확정은 `datasets` 행을 정의 변경과 같은 `lock_dataset`(`FOR NO KEY UPDATE`)로 잡는다. 입력 쓰기(`FOR SHARE`)는 가져오기가 끝날 때까지 기다리다 `lock_timeout` 뒤 503 `WRITE_BUSY`이므로 "가져오기 중 같은 데이터셋 입력 차단"(03b 3-6 BY)을 만족한다 [결정]. 순서는 06 §5와 같다: `datasets` 행 → `ds_` 행(기존 행 `row_id` 오름차순 갱신 → 새 행 기간 오름차순 삽입) → 감사 INSERT → 커밋 |
| 쓰기 방식 | **1,000행 배치 `INSERT ... RETURNING`**(SQLAlchemy 2의 insertmanyvalues). RETURNING이 없으면 pg8000이 행마다 왕복해 100,000행이 86.5초 [실측]. 기간 충돌은 미리 `IN` 조회(5,000개 0.11초 [실측])로 모으거나 `ON CONFLICT DO NOTHING RETURNING`에서 빠진 행으로 판정 |
| 메모리 | 변환·검증 결과를 **전부 보관하지 말고** 1,000행 배치로 흘려보낸다: 2,000,000칸 전량 보관 260MB(칸당 약 116바이트) vs 스트리밍 40MB [실측] |
| 전부 취소 | 오류 목록이 하나라도 있으면 쓰기 전에 422(미리보기와 같은 계산). 충돌(기존 기간)은 `PASTE_CONFLICT`와 같은 `conflicts[]` 형식을 쓰는 새 코드 `IMPORT_CONFLICT`(409) [제안: 새 코드] |
| 동시 실행 | 전역 1건 + 사용자당 1건. 초과는 429 `IMPORT_BUSY` + `Retry-After`(`HeavyReadLimiter` 선례, `backend/app/core/limits.py`) [제안]. 같은 프로세스 안 동시 2건은 GIL 때문에 시간이 2.3배라는 기존 실측(03c X-27)이 있다 [결정 인용] |
| 시간 | 확정 목표 30초(03b Z10). 5MB 전형(60만 칸): 파싱·검증 5~9초 + 적재 약 6초 = 11~15초 [추정: 합산]. **셀 2,000,000칸은 19+18 = 37초 > 30초** [실측 합산]. 협조적 시간 확인(행마다 `monotonic`)으로 45초에서 중단하고 롤백 [제안]. 프록시 타임아웃은 미확인(deploy-coordination 10번) [확인 못 함] |
| 감사 | **사용자 결정 필요(Q11).** 03b 29-1 ②는 "행 값 수정은 기록하지 않음"이다. 가져오기는 한 번에 수만 행을 쓰고 되돌릴 행 삭제가 없어 성격이 다르다. 선택: (a) 기록 없음, (b) **요약 1건** `dataset.import`(권장: 건수·파일 해시 앞 12자·이력 번호만, 행 값 없음), (c) 행별(금지: 크기·`details` 규칙). (b)는 `ck_audit_log_action` 교체(20 → 21개)와 04 부록 A-3·06 §2-1·04 §5-1 갱신을 부른다 |
| 이력 표 | 브리프 4.2·Z11이 "원본 파일 이름·크기·해시 같은 정보 보관"을 이미 승인 [결정] → 정적 표 `dataset_imports` 필요 [제안]: `id`, `dataset_id`(FK), `imported_by`(FK users), `imported_at`, `file_name`(basename만, NFC, 제어문자 제거, 255자), `file_size`, `file_sha256`, `sheet_name`(100자), `orientation`, `rows_created`, `rows_updated`, `rows_skipped`, `mapping`(jsonb 4,000바이트 이하, 같은 양식 재업로드 때 재사용, Q10). 파일 본문·셀 값 미보관. `bi_app`에 `SELECT, INSERT`만(UPDATE·DELETE 없음), `bi_readonly` 없음 |
| 마이그레이션 영향 | revision `0010`: 표 1개 + 인덱스 + GRANT 1줄 + (감사 (b) 선택 시) CHECK 교체. upgrade에 `DROP` 없음. downgrade는 `drop_table`(+`drop_constraint`)을 가져 `DROP_APPROVED`에 **사용자 확인** 필요(0007~0009 선례). downgrade 사전 점검: 이력·`dataset.import` 감사 행이 있으면 한국어 메시지로 거부 [제안] |
| 권한 | 1단계: 기존 데이터셋은 입력(팀)과 같음. 이력 열람은 읽기(Q12). 05 §4 권한 매트릭스와 시험 행 추가 필요 |
