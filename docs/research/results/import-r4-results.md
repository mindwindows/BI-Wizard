**이 문서의 모든 수치는 합성 데이터로 잰 값이다. 실제 회사 엑셀 파일로 검증하지 않았다.** "확인" = 이번 실험에서 직접 관찰한 것, "추정/외삽" = 관찰 값에서 계산한 것, "미시험" = 하지 않은 것.

## 0. 먼저 읽을 결론

1. **정상 파일 메모리는 작다.** read-only 모드(`data_only=True`, `keep_links=False`) 증가분이 5MB 24MB, 10MB 49MB, 20MB 98MB(전형적인 한글·숫자 혼합 표). 3.R 추정 "10MB ≈ 90MB"는 총 RSS 기준으로 맞았다(실측 77MB). 일반 모드는 5MB 253MB, 10MB 480MB로 이전 실측(265MB, 491MB)과 일치 → **일반 모드 사용 금지 유지**.
2. **공유 문자열이 전부 다른 짧은 문자열인 10MB 파일(최악 사례)은 증가분 169MB, 열기만 10.7초**(전형 표의 3.4배). 메모리·열기 시간은 파일 크기가 아니라 **공유 문자열 개수**에 비례한다. 계획은 "파일 크기 1MB당 5MB(전형) ~ 17MB(최악)"로 잡아야 한다.
3. **시간:** 10MB 전형 표 미리보기 3.2초, 전체 훑기 8.8초(파싱만, DB 적재 미측정). 최악 10MB는 미리보기 11.5초, 전체 15.8초. **한 프로세스 안에서 스레드로 동시 2건이면 시간이 2.3배(전형 10MB 18~20초), 3건이면 4배(31~34초)** — GIL 때문에 병렬 이득이 없다.
4. **`iter_rows(max_row=, max_col=)` 상한은 변조 파일을 막지 못한다(HZ1의 ④번 서술이 틀렸다).** openpyxl read-only는 `load_workbook` 시점에 **모든 시트의 `<dimension>`을 읽는데, 시트 XML에 `<dimension>`이 없으면 시트 전체를 끝까지 파싱한다**(소스 확인 + 실측). 그래서 압축 후 0.7MB·해제 300MB인 파일이 `max_row=1000`으로도 37초·RSS 883MB를 쓰고, 800MB는 **컨테이너 1g 제한에서 OOM kill**(45초)이다. 공백 900MB·셀 텍스트 500MB는 **3.5~4.7초 만에 OOM kill**(3회 모두).
5. **그러나 사전 검사(zip 중앙 디렉터리의 해제 크기 합·압축률·항목별 크기)는 시험한 모든 폭탄을 2~3ms에 거부했다.** 정상 파일 최대 압축률은 9.3, 폭탄은 339 이상이라 구분 폭이 크다. 선언 크기를 속인 zip은 사전 검사를 통과하지만 Python 3.12 `zipfile`이 선언 크기까지만 읽고 CRC 오류(`BadZipFile`)로 끝나 **메모리가 늘지 않았다**.
6. **XML 엔티티:** 이 이미지(Python 3.12.15, expat 2.8.5, lxml 없음)에서는 `defusedxml` 없이도 billion laughs·이차 확장은 expat의 증폭 한도(`limit on input amplification factor`)로, 외부 엔티티는 `undefined entity`로 **거부**됐다(canary 파일 내용 미유출). `defusedxml`을 설치하면 openpyxl이 자동으로 쓰며 DTD 엔티티 선언 자체를 `EntitiesForbidden`으로 거부한다. 방어의 근거가 베이스 이미지의 expat 버전에 있다는 점이 한계다.
7. **프록시:** 로컬 frontend nginx는 `client_max_body_size`가 없어 기본 1m가 적용되고, 실행 중 컨테이너로 확인한 결과 **1MiB 초과 본문은 413**(5MB·10MB 포함). 멀티파트는 1MiB 파일도 거부(오버헤드 약 251바이트). 시험용 설정 복사본에 `11m`을 두면 10MiB 파일(멀티파트 포함)이 통과하고 11MiB는 octet-stream만 통과, 멀티파트는 413.
8. **HZ 판단(5절 표):** 사전 검사를 강화한 HZ1(해제 크기·압축률·항목 수·시트 수·DTD·`<dimension>` 규칙)이 시험한 모든 입력을 막았다. 남는 위험은 **한도 안쪽의 완만한 폭탄**(해제 150MB, 비율 50 이하)이며, 이때 한 요청이 약 435MB·19초(외삽)를 쓰므로 **전역 동시 1건(HC1)이 사실상 필수**다. HZ2(별도 프로세스)는 열기 단계를 협조적으로 중단할 수 없다는 점(시간 제한 불가)과 한도 상향 시에만 필요해진다.

## 3. 경계 시험: 행 100,000 · 열 100 · 셀 2,000,000 (3회)

| 파일 | 결과 | 시간 평균/최대 | 최대 RSS |

- 열 상한은 **한 행(101번째 칸이 비어 있지 않음)** 만 보고 판정한다. 상한 밖 열에 값이 있는 행이 처음 나올 때까지는 읽는다.

관찰:
- **dimension 없는 시트는 열 때 전부 파싱한다**(`ReadOnlyWorksheet.__init__` → `_get_size` → `parse_dimensions`가 `iterparse`의 `end` 이벤트로 `sheetData` 끝까지 간 뒤에야 "dimension 없음"으로 판단. 소스 `_read_only.py:44-50`, `_reader.py:172-186`). 미리보기 1,000행만 읽어도 소용없다. 정상 파일에서 `<dimension>`만 지운 변형은 열기 시간이 약 2배(tall 5MB 미리보기 3.0s vs 2.0s, 10MB 5.7s vs 3.2s, 20MB 12.3s vs 5.9s), 메모리는 동일.
- 해제 크기당 메모리: 행 반복 약 2.9MB/MB(300MB → 883MB), 공백·셀 텍스트·짧은 문자열 표는 300MB 이하에서도 1GB를 넘음. **파싱 속도는 해제 크기 기준 약 6~8MB/s**(300MB 37s, tall 10MB 54MB 8.3s).
- 선언 크기 속임: Python 3.12 `zipfile`은 **선언 `file_size`까지만 읽고 EOF에서 CRC를 검사**해 `BadZipFile`을 낸다. 선언보다 많이 풀리지 않는다(A-24 확인). 단 이는 3.12.15 한 버전의 관찰이다.
- OOM kill은 컨테이너의 가장 큰 프로세스를 죽인다. **backend가 한 프로세스(PID 1)이면 backend 자체가 죽는다.** 확인: `bomb_rows_1gb`를 PID 1로 돌린 컨테이너(`--restart=unless-stopped`, 75초 뒤 `RestartCount=1`)는 프로세스 사망 후 재시작됐다(그 시점의 `OOMKilled` 플래그는 재시작으로 초기화돼 관찰하지 못함, 앞의 cgroup `oom_kill` 카운터 증가와 같은 원인으로 해석).
- 같은 cgroup에서 폭탄(별도 프로세스)과 정상 요청을 동시에 돌리면 OOM killer가 **폭탄(가장 큼)을 죽이고** 정상 요청(tall 10MB, 8.5s)은 끝까지 성공했다(1회 관찰, 보장 아님).

### 5-3. 강화 사전 검사(`precheck2`)와 거짓 양성
사전 검사에 ① 각 XML 항목 앞 4KB에서 `<!DOCTYPE`/`<!ENTITY` 검색, ② 시트 XML 앞 4KB에 `<dimension>` 존재 확인(없으면 거부), ③ UTF-16 BOM 의심을 더했다. 시험 파일 62개(3회씩):
- 정상형 29개(tall/wide/wide100/fmt/multi 각 3, 경계 7, sst_unique_big, cell_long_string, cols_10000, cols_16384_rows_20, dim_false 계열 3) **모두 통과(거짓 양성 0)**, 시간 3ms 안팎. (uniq_short는 강화 검사를 돌리지 않았고 기본 사전 검사는 통과.)
- 거부 33개: 변조·위장 30개 + 정상에서 `<dimension>`만 지운 변형 3개. 변조 파일은 모두 거부. 선언 크기 속임 2개는 앞 4KB를 읽는 과정에서 `BadZipFile`로 거부(0.3s는 import 포함).
- **거짓 양성이 생기는 곳:** 정상 파일에서 `<dimension>`만 지운 변형(`nodim_tall_*`)은 ②로 거부된다. 이런 파일은 열기만 약 2배 느릴 뿐 안전하므로 **dimension 없음은 "거부"보다 "시트 해제 크기 상한 이내만 허용"이 더 낫다**(판단).

| 선언 크기 속임 | – | `zipfile`이 선언 크기에서 멈춤(확인). 앞 4KB 읽기로 조기 거부도 가능 | 불필요 |

| 시트 수 과다 | 시트 수는 workbook.xml에서 미리 센다 | 시트 수 ≤ 30(HL), workbook.xml 크기 상한 | 불필요 |
| 형식 위장·암호화·매크로·경로 이름 | 서명·필수 항목·`vbaProject.bin`·이름 규칙으로 거부 | 위와 같음 | 불필요 |
| **한도 안쪽의 완만한 폭탄**(해제 150MB, 비율 ≤ 50) | 막지 못함 | 한 요청이 **약 435MB·19초(외삽: 300MB 실측 883MB·37초에서 선형 가정, 미시험)**. 동시 1건이면 1g 안, **동시 2건이면 OOM 위험** → **HC1(전역 1건) 필수**. 열기 단계 19초는 미리보기 내부 타임아웃 20초에 근접하고 협조적으로 중단할 수 없다 | `RLIMIT_AS`로 백스톱. 시험: `RLIMIT_AS=700MB` 자식이 폭탄에서 `MemoryError`로 **스스로 종료**(rc 0, RSS ≤ 695MB, 2.5~58s). 같은 설정에서 정상 10MB는 영향 없음(77MB). 비용: 프로세스당 파이썬+openpyxl import 약 0.3s(미리 띄운 워커 풀·fork로 줄일 수 있음, 미시험) |
| 서버 메모리/시간 보장 | 불가(열기 단계) | 부분 | **HZ2만 가능** |

판단(근거는 위 표, 결정은 사용자):
- **HZ1 원안은 불충분하다.** 사전 검사 항목의 상한 값과 dimension·DTD 규칙을 넣은 **HZ1′**가 시험한 입력을 모두 막는다.
- HZ1′ + **HC1(전역 동시 1건)** 이면 한도 안쪽 최악 입력도 1g 안에 들어온다(외삽). 한도를 올리거나(20MB 이상) 동시 2건 이상을 허용하면 **HZ2로 올려야** 한다. 또한 **응답 시간 상한(50초)을 열기 단계까지 강제하려면 HZ2뿐**이다.
- HZ2를 고르지 않으면 "한도 안쪽 폭탄 1건이 약 19초·435MB를 쓰고, 그동안 backend의 다른 요청이 GIL 경합으로 느려진다"는 위험을 알고 가는 것이다.

## 6. 프록시 본문 상한 (X-27 4절)

**코드 확인:** `frontend/nginx/templates/default.conf.template`에는 `client_max_body_size` **지시자가 없고** 13번째 줄에 "업로드 크기 상한(Gate ③ 결정)이 정해질 때 설정한다(nginx 기본 1m)"는 주석만 있다(`nginx -T` 출력에서도 지시자 부재 확인). `proxy-common.conf`에도 없다.

**실행 확인:** `bi-wizard-frontend:local`(nginx 1.28.3)을 `docker run`으로 별도 기동(`g3x27-frontend`, `APP_BASE_PATH=/bi-wizard`, 가짜 업스트림 `backend`는 요청 본문 바이트 수를 돌려주는 파이썬 서버). 시험용 설정 복사본(`client_max_body_size 11m;` 한 줄 추가)은 별도 컨테이너 `g3x27-frontend-11m`에 마운트. 저장소 파일은 수정하지 않았다. 본문 형태 3종: octet-stream, `curl -F`(멀티파트), `Transfer-Encoding: chunked`.

| 본문 크기 | 기본(미설정=1m) octet / 멀티파트 / chunked | `11m` 복사본 octet / 멀티파트 / chunked |
| --- | --- | --- |
| 0.9MiB | 200 / 200 / 200 | 200 / 200 / 200 |
| 1MiB 정확히 | 200 / **413** / 200 | 200 / 200 / 200 |
| 1MiB + 1B | **413** / 413 / 413 | 200 / 200 / 200 |
| 2MiB | **413** / 413 / 413 | 200 / 200 / 200 |
| 5MiB | **413** / 413 / 413 | 200 / 200 / 200 |
| 10MiB | **413** / 413 / 413 | 200 / 200 / 200 (업스트림이 10,485,760바이트 수신) |
| 11MiB 정확히 | 413 / 413 / 413 | 200 / **413** / 200 |
| 11MiB + 1B | 413 / 413 / 413 | **413** / 413 / 413 |
| 12MiB | 413 / 413 / 413 | 413 / 413 / 413 |
- **현재 구성은 1MiB 초과 업로드를 모두 413으로 거부**한다(5MB 포함) → H-5의 추정이 확인됨. Gate ④ 전에 env 작업으로 설정해야 한다.
- 멀티파트는 파일 외에 약 251바이트가 더 붙어(10MiB 파일 → 10,486,011바이트) **상한과 같은 값으로 두면 상한 크기 파일이 거부된다.** 상한 + 1MiB 여유가 필요하다(HV 전 계층 값 정합 시 반영).
- chunked(Content-Length 없음)도 같은 한도로 거부됨(nginx가 수신 중 계산). 응답 본문은 nginx HTML(JSON 아님)이므로 프런트는 413을 JSON으로 가정하지 말아야 한다.
- 메인 플랫폼 프록시의 실제 한도·타임아웃은 재현 불가(DC 7·10번).

## 7. H-3 추정 갱신과 `mem_limit` 1g 판정

### 7-1. 갱신 표 (read-only, `data_only=True`, `keep_links=False`; 단위 MB)
Δ = 기준 RSS 초과분(파싱이 backend 프로세스 안에서 쓰는 증가분에 해당). "실측"은 3회 평균, "외삽"은 선형 가정.

| 파일 | 형태 | 1건 Δ | 1건 총 RSS(기준 27.5 포함) | 동시 2건(프로세스) | 동시 3건(프로세스) | 일반 모드 |
| --- | --- | --- | --- | --- | --- | --- |
| 5MB | 전형(tall) | 24 (실측) | 52 (이전 추정 45와 근접) | cgroup 111 | 157 | 253 (이전 265) |
| 10MB | 전형 | 49 (실측) | 77 (이전 추정 약 90) | 160 | 230 | 480 (이전 491) |
| 10MB | **최악 sst 밀집(uniq_short)** | **169 (실측)** | 197 | 스레드 2건 357~361 | 미측정 | 미측정 |
| 20MB | 전형 | 98 (실측) | 126 (이전 추정 약 180) | 260 | 377 | 미측정(외삽 약 960) |
| 20MB | 최악 sst 밀집 | 약 340 (**외삽**, 미측정) | 약 370 | 약 700 | 약 1,050 | – |
- 동시 N건의 cgroup 값은 프로세스마다 기준 28MB가 더해진 값이다. 한 프로세스 안 스레드에서는 기준이 한 번만 든다(스레드 시험: 2건 125MB, 3건 170MB).
- 이전 추정은 "선형 가정"이었다. 전형 표에서는 맞거나 과대, **sst 밀집 파일은 3.4배 과소**였다. 파일 크기에 대한 계획 기울기는 **전형 5MB/MB, 최악 17MB/MB**.

### 7-2. 10MB 상한에서 `mem_limit` 1g 여유 (backend 유휴 53MiB 가정, 현재 코드 기준)
| 시나리오 | 메모리(근사) | 한도 대비 | 판정 |
| --- | --- | --- | --- |
| 전형 표 1건 | 53 + 49 = 약 100MB | 10% | 여유 충분 |
| 전형 표 2건 | 약 150MB | 15% | 충분 |
| 최악 sst 밀집 1건 | 53 + 169 = 약 220MB | 22% | 충분 |
| 최악 2건 | 53 + 338 = 약 390MB | 38% | 충분(시간이 문제: 36초) |
| 최악 3건 | 약 560MB | 55% | 메모리는 가능, 시간 부적합(34~54초 추정) |
| 한도 안쪽 폭탄 1건(해제 150MB, 외삽) | 53 + 435 = 약 490MB | 48% | 가능 |
| 한도 안쪽 폭탄 2건 | 약 920MB | 90% | **OOM 위험** → HC1 필수 |
- **메모리 기준으로는 10MB 상한·동시 1~2건이 1g에 충분히 들어간다.** 제약은 **시간**(스레드 동시 시 GIL로 직렬 이상으로 느려짐)과 **한도 안쪽 폭탄**이다.
- 20MB 상한은 전형 표는 1건 약 150MB, 최악·폭탄 한도(300MB 해제)에서는 1건 약 900MB로 1g 한도에 근접(폭탄 한도는 외삽) → 20MB는 HZ2 없이 권하기 어렵다.
- 시간: 파싱만 전형 10MB 미리보기 3.2s + 확정 훑기 8.8s(HT2는 둘 다 파싱), 최악 10MB 11.5s + 15.8s. **HP1 설계 목표(확정 30초 이내)는 적재 시간을 포함해야 판정할 수 있는데 이번에 적재를 재지 않았다.** 파싱만으로 최악 10MB가 16초(목표의 53%)이고 스레드 동시 2건이면 36초다.
- `RequestBodyLimitMiddleware`: 이미지의 Starlette 1.7.0에 `starlette.middleware.body_limit` 모듈이 존재한다(`import` 성공)는 것만 확인했다. 동작 시험은 안 했다.
- 새 의존성 확인: backend 이미지에는 `python-multipart`가 없고, FastAPI가 `UploadFile` 파라미터를 선언하는 순간 `RuntimeError: Form data requires "python-multipart"`를 낸다(실행 확인). 업로드 구현에는 `python-multipart`가 필요하다 → 새 런타임 의존성(승인 필요), `openpyxl`·`defusedxml`(선택)과 함께.

## 10. 한계와 확인하지 못한 것

1. **합성 데이터만 사용.** 실제 업무 엑셀(열 수, 문자열 비중, 압축률, `<dimension>` 유무, 외부 링크 빈도)로 재보정이 필요하다. 압축률 한도(50)와 해제 크기 한도는 특히 실제 파일의 분포를 모른다.
2. **적재 시간(pg8000 INSERT)·동기 확정 총 시간·HZ2 프로세스 격리 프로토타입·`RequestBodyLimitMiddleware` 413**은 이번 범위에 없어 측정하지 않았다(X-27 원안 중 남은 부분). HP1 "확정 30초 이내" 판정은 이 값들이 있어야 한다.
3. 시간 값은 4코어 호스트에서 다른 에이전트의 컨테이너가 도는 상태에서 쟀다. 절대값은 ±20% 정도 흔들릴 수 있다(같은 조건 3회 간 차이는 대체로 5% 안쪽이었다). CPU 제한 없이 시험했다(compose에도 `cpus` 제한 없음).
4. 큰 변조 파일의 전체 훑기는 1회만 쟀다(공백·셀 텍스트는 3회). 한도 안쪽 폭탄의 435MB·19초는 **300MB 실측 두 점에서 선형 외삽**한 값이다.
5. 병합 셀(read-only는 무시)·수식(캐시 값 의존, 캐시가 없으면 `None`)은 openpyxl이 만든 합성 파일로만 봤다. Excel이 저장한 실제 파일의 XML 변형(`xml:space`, `rich text`, 임베디드 서식 등)은 미시험.
6. `defusedxml` 동작은 0.7.1에서만, 표준 파서 동작은 이 이미지의 expat 2.8.5에서만 확인했다. 베이스 이미지가 바뀌면 재시험이 필요하다. lxml이 설치되면 openpyxl이 lxml 경로를 써서 동작이 달라질 수 있다(이미지에는 lxml 없음).
7. OLE2 암호화 판정은 서명만 본다. 구형 `.xls`도 같은 서명이라 구분되지 않는다(둘 다 거부 대상이면 문제없음). 암호화 zip 항목(플래그 비트)·zip64·다중 디스크는 미시험.
8. **절차 이탈 1건:** 작업 초반에 읽기 전용 `git check-ignore`와 `git status --short`를 실행했다(`_workspace/`가 Git 제외인지, 새 폴더 상태 확인용). 금지 목록의 "git 사용"에 해당하므로 보고한다. 파일 변경은 없었다.
