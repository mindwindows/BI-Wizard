# 메인 플랫폼 운영자에게 확인할 질문 (인증·신원·프록시)

- 상태: **사용자 검토 대기** (2026-10-11 Gate ③ 1라운드 결정 U2). 사용자가 검토해 직접 답할 수 있는 것은 답하고, 남은 질문은 사용자가 운영자에게 전달한다.
- 핵심 10개: 1, 2, 5, 7, 8, 9, 13, 14, 15, 16번(**[핵심]** 표시). 나머지는 해당 방식이 정해질 때나 배포 협의 때 확인해도 된다.
- 괄호 안 `N번`은 `docs/deploy-coordination.md`의 항목 번호(내부 참조)이므로 전달할 때 지워도 된다. 경로 예시 `/bi-wizard/`는 실제 값이 협의 전이다(`deploy-coordination.md` 1번).
- **1라운드 결정에 따른 조정:** 팀 소속은 포털 안에서 관리자가 지정하므로(`docs/decisions/03b-gate3-round-decisions.md`) 메인 플랫폼에서 꼭 받아야 하는 사용자 정보는 **변하지 않는 식별자**(5번 ①)와 이름(②)뿐이다. 5번의 ④⑤⑥(부서·직급·역할/그룹)과 14, 15번은 "있으면 활용, 없어도 무방"이다. 14, 15번은 핵심이지만 답이 "없다"여도 진행에 지장이 없다.
- 근거 문서: 비교안 `_workspace/gate3/round1-options.md` 1-5절(Git 제외). 8번 방식은 이 질문들의 답을 받은 뒤 결정한다.

**A. 신원을 넘기는가**
1. **[핵심]** 메인 플랫폼은 사용자를 로그인시켜 관리합니까? 우리 서비스의 하위 경로(예: `/bi-wizard/`, 실제 경로는 `deploy-coordination.md` 1번에서 협의)의 요청을 **인증된 사용자만** 도달하게 할 수 있습니까? (인증 안 된 요청의 응답 방식은 11번에서 묻습니다.)
2. **[핵심]** 하위 서비스에 로그인한 사용자의 신원을 넘기는 표준 방식이 있습니까? (요청 헤더, 서명된 토큰, 쿠키, 조회용 API, OIDC/SAML 등) 이미 같은 방식을 쓰는 다른 하위 서비스의 사례나 문서가 있습니까?

**B. 형식과 내용**
3. 헤더라면 **정확한 헤더 이름, 값 형식, 한글 등 비ASCII 값의 인코딩 방식**은 무엇입니까?
4. 서명된 토큰이라면 형식(JWT 여부), 서명 알고리즘, **검증용 키를 어떻게 받는지**(공개키 주소, 공유 비밀. Secret 주입 방식은 `deploy-coordination.md` 11번과 같이 정합니다), issuer/audience, 만료 시간, 갱신 방식은 무엇입니까? 쿠키·토큰을 우리 서버가 **플랫폼의 조회 API로 검증**하는 방식이 있다면 그 주소와 인증 방법도 알려 주십시오.
5. **[핵심]** 어떤 사용자 정보가 옵니까? ① **변하지 않는 식별자**(사번, 로그인 ID, 이메일 중 무엇이 불변입니까) ② 이름 ③ 이메일 ④ 부서/팀(코드와 이름) ⑤ 직급 ⑥ 역할/그룹(목록이면 형식은?)
6. 식별자가 바뀌는 경우(개명, 부서 이동, 휴직, 퇴사)를 우리 서비스가 어떻게 알 수 있습니까? 퇴사자 비활성화는 어떻게 반영됩니까?

**C. 신뢰 경계**
7. **[핵심]** 우리 서버로 들어오는 경로가 메인 플랫폼 프록시뿐임을 **네트워크로 보장**할 수 있습니까? 프록시는 우리와 같은 호스트입니까, 다른 서버입니까? 프록시의 출발 IP는 무엇입니까? (20번)
8. **[핵심]** 클라이언트가 보낸 **같은 이름의 신원 헤더와 `X-Forwarded-*`를 프록시가 제거하고 자기 값으로 덮어씁니까?** (8·14번)
9. **[핵심]** 프록시와 우리 사이 구간은 TLS입니까? 프록시가 **공유 비밀 헤더**를 추가하거나 mTLS를 쓸 수 있습니까? (8번)
10. `X-Forwarded-For`를 전달합니까? (19번: 안 보내면 Superset 기본 속도 제한이 모든 사용자를 한 IP로 집계합니다)

**D. 세션과 로그아웃**
11. 플랫폼 세션의 만료 시간과 슬라이딩 여부는? 만료된 뒤 **fetch(XHR) 요청**은 로그인 HTML(302)을 받습니까, 401 JSON을 받습니까?
12. 사용자가 플랫폼에서 로그아웃하면 하위 서비스가 해야 할 일이 있습니까? 하위 서비스 화면에 로그아웃 버튼이 필요하면 이동할 플랫폼 로그아웃 URL은?
13. **[핵심]** 플랫폼 쿠키의 **이름, 도메인, Path, SameSite**는 무엇입니까? 이름이 `session`인 쿠키가 있습니까? (15번)

**E. 권한과 Superset 관리 화면**
14. **[핵심]** 플랫폼에 "이 서비스를 쓸 수 있는 사용자 그룹"을 부여·회수하는 기능이 있습니까? 없으면 우리가 허용 목록을 관리하겠습니다.
15. **[핵심]** 플랫폼의 관리자 계정을 우리 서비스의 관리자로 간주하는 규칙을 둘 수 있습니까(전달되는 역할 값으로)?
16. **[핵심]** Superset 경로(`/bi-wizard/superset/` 아래)는 두 부류로 나뉩니다. 경로 단위 규칙으로 구분할 수 있습니까?
    - 16-a. **로그인·관리·작성 화면**(예: `…/superset/login/`, 대시보드·차트·데이터셋 목록, 차트 작성(Explore), SQL Lab. 실제 경로 목록은 구현 때 확정)만 **특정 사용자 그룹에게 제한**할 수 있습니까?
    - 16-b. 포털에 임베드된 대시보드가 쓰는 **`…/superset/embedded/*`, `…/superset/static/*`, 임베드 대시보드가 호출하는 `…/superset/api/v1/*`는 모든 포털 사용자의 브라우저에 열려 있어야** 합니다(`deploy-coordination.md` 4번). 이 경로들을 막지 않고 16-a만 제한하는 규칙이 가능합니까? 불가능하면 Superset 경로 전체를 제한 없이 노출하는 것을 수용할 수 있습니까? (참고: `…/api/v1/*`는 관리 화면과 임베드가 같이 쓰므로 경로 규칙만으로 둘을 가르기 어려울 수 있어, 실질적으로 제한 가능한 것은 화면(HTML) 경로뿐일 수 있습니다. 전체를 노출해도 guest 토큰이 없으면 Superset은 자체 로그인을 요구합니다. 단 `Public` 역할에 권한이 있는 `@protect` API는 예외, S11.)
    - 경로는 접두를 떼지 않고 그대로 전달되어야 합니다(3번).
17. 사내 SSO(OIDC/SAML IdP)가 있습니까? 하위 서비스를 클라이언트로 등록할 수 있습니까(절차, 리다이렉트 URI 제한)? Superset도 별도 클라이언트로 등록할 수 있습니까?

**F. 환경과 정책**
18. 신원 전달을 로컬에서 재현할 **시험용 환경이나 샘플 요청**(헤더 예시, 테스트 계정)을 받을 수 있습니까?
19. 플랫폼이 응답에 붙이는 보안 헤더(`X-Frame-Options`, CSP `frame-ancestors` 등)가 포털 안의 Superset iframe(Embedded)에 영향을 줍니까? (9번)
20. 사내 정책상 접속 로그에 사용자 신원을 남겨야 합니까? 로그 보존 기간은?
